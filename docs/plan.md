# План реализации

Рабочий документ: этапы, принципы и решения, принятые по ходу. Из раздела решений в конце
собираются заметки для сдачи (`NOTES.md`).

## Принципы

- **Нарезка — гибрид.** Небольшой фундамент, затем вертикальные этапы по эндпоинтам (от схемы
  до тестов), сквозные механизмы — идемпотентность, ограничение частоты, кэш — отдельными этапами.
- **Готовность этапа:** сборка зелёная; тесты этапа написаны и проходят; тесты прошлых этапов
  не сломаны; приложение стартует на чистой базе (`docker compose down -v`); отдельный коммит.
- **Миграции — по этапам.** Схема меняется в том этапе, которому она нужна.
- **Решения записываются сразу** — в раздел этапа ниже; в коде — пометкой `// решение:`.
- **Обвязка тестов растёт по мере надобности** — каждый этап добавляет ровно то, что ему нужно.
- **Код пишем в стиле ponytail** — самое маленькое полное изменение, без абстракций «на потом».
  Правило ТЗ о комментариях главнее: в коде только `// решение:`, без `shortcut:` и прочих.

## Общая проверка этапа

```
docker compose up -d
dotnet build
dotnet test
```

## Этапы

### 0. Окружение и тесты существующего кода — готово

- Окружение: .NET 9 SDK, Postgres и Redis из `docker compose`, приложение стартует,
  `/health` и `/auth/login` работают.
- Обвязка тестов: общий хост приложения на прогон (`ApiHost`), вход и авторизованный клиент
  (`AuthClient`), отдельная одноразовая база (`ScratchDatabase`).
- Тесты существующего: запуск и Swagger; вход (роли, неверный пароль, неизвестный email,
  пустое тело); сиды на отдельной базе (точные количества по константам, инварианты броней
  и абонементов, повторный запуск ничего не меняет); репозитории; `RedisCacheService`.

## Решения

### Этап 0

- Сиды проверяются на отдельной свежей базе: общая база прогона меняется другими тестами,
  а точные количества верны только сразу после заполнения.
- Количества пользователей, залов и занятий в тестах сидов — литералы, а не константы сидера:
  ТЗ запрещает менять состав начальных данных, и тест должен падать, если их поменяли.
  Ссылка на константу сделала бы его тавтологией. Логины `user001@club.test` — тоже часть
  контракта из `README`.
- Число броней в сидах не проверяется — оно зависит от генератора; проверяются инварианты.
- Ловушку с фильтром проверяем на данных, вставленных самим тестом, а не на случайно
  подходящих строках из сидов.
- Тестовые ключи Redis не убираем вручную: у них есть TTL, а база Redis чистится в начале прогона.

## Замеченные ловушки

- `ClassConfiguration` вешает `HasQueryFilter(!IsCancelled)`: отменённое занятие не находится
  через репозиторий, а бронь на него пропадает при `Include(x => x.Class)` — без `Include`
  она загружается. Зафиксировано тестами `RepositoryTests`. Нужен `IgnoreQueryFilters()`
  там, где отменённое занятие должно быть видно (отказ `class-cancelled`, карточка, отмена брони).
- Ограничение маршрута `{id:long}` даёт `404` на нечисловой id, контракт требует `400`.
- Ненулевые числовые поля тела при отсутствии становятся `0` — нужен `[Required]` на nullable.
- В карточке брони лежит остаток абонемента: он меняется от любых операций пользователя,
  в том числе от продвижения очереди.
- Postgres хранит время с точностью до микросекунды, .NET — до 100 нс.
- Лимит 60 запросов в минуту на пользователя будет мешать тестам — его нужно сделать настраиваемым.
