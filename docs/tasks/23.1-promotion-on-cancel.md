# 23.1 Продвижение при отмене (§3)

Статус: готово (fa7e1a5)

- под замком занятия: очередь, затем абонементы одним запросом `ORDER BY id FOR UPDATE` (в [задаче 23](23-waitlist-promotion.md)).
  Свой абонемент входит в этот запрос: отдельный замок своего абонемента из 12.3 и 14.3
  заменяется, иначе общий порядок по id нарушен и встречные отмены дают взаимоблокировку;
- порядок в транзакции (задача 23, «Замки и часы»): занятие → бронь → очередь → все абонементы
  → `now` → `class-started`; на отменённом клубом занятии очередь не читается, блокируется
  только свой абонемент;
- по решению задачи 21 (заметки, «Порядок продвижения») раздаются все свободные места после
  отмены, `capacity − занятые`, включая простаивавшие раньше; очередь проходится целиком
  по `id`, кому не хватает мест — пропускается и остаётся `waiting`, стоящие за ним
  продвигаются; запись больше вместимости пропускается так же; ожидающий становится активной
  бронью, его посещения списаны; в базе мест не больше вместимости, остатки не в минусе;
- бронь продвинутого — с id его записи в очереди (задача 18), первый тест подзадачи: до
  продвижения `GET /enrollments/{id из §7}` — `404`, после — `200`, точные `seats`,
  `status: active`, `createdAt` — момент продвижения (`app.Clock`), не время постановки;
  повтор §7 с тем же ключом после продвижения отдаёт тот же `id`;
- продвинутая запись очереди — `status = promoted` (задача 19), `cancelled_at` пуст; стоявшие
  за ней поднимаются; §8 по ней — `409 already-promoted`;
- ожидающий, которому мест хватает, но посещений меньше, чем мест в записи, или абонемент
  истёк на момент операции (граница — последний день `validUntil`), пропускается и остаётся
  `waiting`, следующие продвигаются; места сверяются раньше абонемента, срок — раньше остатка;
- ожидающий без абонемента — `500` и откат, очередь и остатки прежние;
- отмена брони на отменённом клубом занятии очередь не продвигает: записи остаются `waiting`;
- отмена на начавшемся занятии — `409 class-started` после замка всех абонементов: бронь,
  очередь и остатки не меняются;
- меньше чем за 2 часа до начала продвижение идёт как обычно, посещения продвинутого
  списываются; граница — ровно 2 часа и на тик меньше;
- самопродвижение (задача 22, заметки «Самопродвижение»): отмена клиентом, у которого на занятии
  своя запись `waiting`, — больше чем за 2 часа и за 2 часа минус тик; своя запись остаётся
  `waiting`, следующий по очереди продвинут, `refundedVisits` и остаток отменившего — строго
  по §3, второго списания нет; если кроме своей записи никого нет — места свободны; затем
  отмена другим клиентом продвигает эту запись как обычно;
- переполненное занятие (задача 1): если после отмены занятых мест не меньше вместимости,
  никто не продвигается;
- `refundedVisits` отменившего не зависит от продвижения;
- unit-тесты плана `WaitlistPromotion.Plan` (задача 23, «Устройство кода»): порядок обхода
  по `id`, пропуск по местам с продвижением стоящих дальше, запись больше вместимости,
  `freeSeats` `0` и меньше нуля, `own-release` раньше мест, `pass-expired` раньше
  `pass-exhausted`, `validUntil` — сегодня (годен) и вчера (истёк), остаток равен местам
  и на одно меньше;
- повторная отмена уже отменённой брони очередь не трогает.

## Нюансы реализации

- допущение задачи 18 подтвердилось: EF Core 9 отправляет явный `Id` брони при вставке, отдельный
  SQL не нужен (первый тест подзадачи);
- пропуск из-за мест в плане — внутренняя причина `no-seats` (`WaitlistPromotion.NoSeats`):
  в 23.4 она не логируется;
- исходы продвижения в `CancelResult` не добавлены: нужны только событиям, это 23.4;
- тесты «продвижения нет» (отменённое клубом занятие, начавшееся, переполненное, повторная
  отмена) на красном прогоне были зелёными — заглушка тоже никого не продвигает; они держат
  регресс после реализации.
