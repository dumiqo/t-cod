# 29.4 Нагрузочный прогон с Redis и без

Не в `dotnet test`: результат зависит от машины, прогон долгий. Запускается вручную,
итог — таблица в заметках для сдачи. Заменяет пункты «ручная проверка скорости
на синтетической базе» и «ручная проверка с остановленным Redis».

- цель — реальный процесс: `dotnet run --project WebApi` (Kestrel) плюс `docker compose`,
  не `TestServer`;
- режимы Redis:
  - работает;
  - остановлен с самого старта (`docker compose stop redis`);
  - остановлен посреди прогона и поднят обратно;
  - завис (`docker pause`);
- что снимаем: p50 / p95 / p99 по каждому эндпоинту, пропускная способность, доли `2xx`,
  `409`, `429`, `503`, `500`;
- критерии: ни одного `500`; лимит 60 в минуту соблюдается в обоих режимах (по пользователю
  проходит не больше 60 не-`429` за любое окно в минуту); после прогона выполняются инварианты
  из 29.3 (проверочный SQL-скрипт); без Redis карточка брони медленнее, но не ломается;
- лимит 60 — константа контракта, поднимать его для прогона нельзя. Чтобы нагрузка
  упиралась в систему, а не в `429`, нужны тысячи синтетических пользователей с абонементами
  и сотни занятий — отдельный скрипт засева для прогона, сиды не меняются;
- инструмент — NBomber (выбор пользователя): отдельный консольный проект рядом с решением,
  не тестовый проект `dotnet test`. При проработке проверить: условия лицензии текущей версии
  для этого использования, какая версия совместима с .NET 9, как задаются ступени нагрузки
  и где лежит отчёт (p50 / p95 / p99, коды ответов); логин пользователей — до сценария,
  токены переиспользуются;
- развилка — что считать порогом p95 и с какой нагрузкой сравнивать: в задании чисел нет,
  порог выбираем сами и пишем как `// решение:` / в заметки;
- найденная ошибка — тест-воспроизведение в `dotnet test` и исправление (TDD), а не правка
  сценария нагрузки.
