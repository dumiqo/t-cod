# 29.4 Нагрузочный прогон с Redis и без

Статус: готово (fb03875)

Не в `dotnet test`: результат зависит от машины, прогон долгий. Запускается вручную,
итог — таблица в заметках для сдачи. Заменяет пункты «ручная проверка скорости
на синтетической базе» и «ручная проверка с остановленным Redis».

- цель — реальный процесс: `dotnet run -c Release --project WebApi` (Kestrel) плюс
  `docker compose`, не `TestServer`. Логи как в поставке (Information, JSON), stdout — в файл:
  по нему считается событие 1005, и консоль не становится узким местом;
- режимы Redis:
  - работает;
  - остановлен с самого старта (`docker compose stop redis` до запуска приложения);
  - остановлен посреди прогона и поднят обратно;
  - завис (`docker pause`) посреди прогона и отпущен;
- что снимаем: p50 / p95 / p99 по каждому эндпоинту, пропускная способность, доли `2xx`,
  `409`, `429`, `503`, `500`;
- критерии: ни одного `500`; лимит 60 в минуту соблюдается во всех режимах; после прогона
  выполняются инварианты из 29.3 (`InvariantChecker`); без Redis карточка брони медленнее,
  но не ломается;
- восстановление — здесь, а не в 29.5: после остановки и подъёма Redis задержки возвращаются
  к исходным, `/health/ready` снова `Healthy`, событие 1005 прекращается;
- при отказе Redis лимит считает журнал в памяти, то есть 60 в минуту на процесс: прогон идёт
  на одном инстансе, и в заметках это ограничение надо назвать явно (нюанс из 29.5);
- лимит 60 — константа контракта, поднимать его для прогона нельзя;
- найденная ошибка — тест-воспроизведение в `dotnet test` и исправление (TDD), а не правка
  сценария нагрузки.

## Инструмент

- NBomber не берём: версия 6.x бесплатна только для personal / academic use, тестовое задание
  для работодателя — серая зона лицензии;
- нагрузка — **k6** (AGPL-3.0, только запускаем, код не распространяем; строка про это —
  в заметки), образ `grafana/k6` через `docker run`, приложение на
  `host.docker.internal:5080`, ставить ничего не нужно. Сценарий — `load/scenario.js`;
- p50 / p95 / p99 — `summaryTrendStats`, разбивка по кодам — тег `status`, построчный CSV —
  `--out csv`; каждому запросу ставится тег `user` (для проверки лимита);
- консоль `WebApi.LoadTests/` в `.sln` (имя с `Tests` — чтобы хук TDD считал её тестовым кодом,
  тестов MSTest в ней нет): засев, логин, разбор результатов. `InvariantChecker` подключается
  ссылкой на файл (`<Compile Include="..\WebApi.Tests\Invariants\InvariantChecker.cs" Link=…>`)
  плюс ссылка на `DataAccessLayer`, не на тестовый проект целиком; SQL-дубля проверки нет.

## База и засев

- отдельная база `club_load`: приложение запускается с `ConnectionStrings__…` на неё, само
  мигрирует и засевает обычные сиды, затем засев прогона дописывает синтетику. Перед каждым
  режимом база пересоздаётся, Redis — `FLUSHALL` (ключи лимитера прошлого режима);
- засев напрямую через `ClubDbContext`: 2000 пользователей с одним заранее посчитанным хешем
  `Password123!`, абонементы на 1000 посещений с `validUntil` через год, 300 занятий на 3–20
  мест на ближайшие 7 дней, часть сразу полные (очередь и `capacity-exceeded`). Сиды не
  меняются;
- снимок начальных остатков для `InvariantChecker` — `load/out/initial-passes.json`;
- логин всех пользователей через `POST /auth/login` до сценария, параллельно, вне замера;
  токены (JWT живёт 720 минут) — в `load/out/tokens.json`, k6 читает их через `SharedArray`.
  Логин в `setup()` k6 не годится: он однопоточный.

## Сценарий и профиль

- основная смесь: карточка 40%, `GET /schedule` 20%, `POST /enrollments` 15%, отмена брони 5%,
  `seats` 5%, вход в очередь 7%, выход из очереди 5%, `GET /analytics/load` под админами 3%
  (эндпоинт только для админа);
- параллельно сценарий «жадных»: 10 пользователей по 2 запроса в секунду — для критерия `429`;
- при ~20 запросах в минуту на пользователя 2000 пользователей дают ~650 RPS без упора в лимит;
- открытая модель: сначала одна калибровка при работающем Redis (`ramping-arrival-rate`
  ступенями), затем рабочая нагрузка = 70% найденной частоты, одна для всех четырёх режимов;
  каждый режим — 5 минут `constant-arrival-rate`, первые 30 с — прогрев, в статистику не идут;
- в режимах «посреди прогона» stop / pause — на 1:30, start / unpause — на 3:00.

## Пороги

Все три числа — `// решение:` в коде прогона и в заметках; в задании чисел нет.

- порог p95 — правило калибровки, а не критерий провала: рабочая нагрузка — наибольшая
  частота, при которой у каждого эндпоинта p95 ≤ 200 мс при работающем Redis. В режимах без
  Redis абсолютного порога нет, p95 только записывается; «не ломается» = нет `500`, лимит
  соблюдён, инварианты целы;
- восстановление: p95 за последнюю минуту после подъёма Redis не больше 1,5× от p95 до
  остановки в том же прогоне; `/health/ready` снова `Healthy`; последнее событие 1005 в логе —
  не позже 10 с после `docker compose start redis`;
- режим «завис» снимается как есть (сейчас каждый запрос ждёт `Redis:OperationTimeout`):
  критерии — нет `500`, лимит, инварианты, задержки записываются. После правки 29.5 этот режим
  перепрогоняется и строка таблицы обновляется — пункт в 29.5.

## Проверка лимита

- по CSV k6 (`user`, начало, конец, статус) для каждого пользователя: у ответов не-`429`
  по порядку нарушение достоверно, если `end[i+60] − start[i] < 60 с` — серверный момент
  лежит между отправкой и ответом. Только такие нарушения роняют критерий;
- пограничные (`start[i+60] − end[i] < 60 с`, но не первое условие) — в отчёт, не провал.

## Оркестровка

`load/run.ps1 -Mode calibrate|running|down|restart|paused`:

1. пересоздать `club_load`, `FLUSHALL` Redis;
2. для `down` — остановить Redis до старта приложения;
3. запустить приложение (Release, stdout в файл), дождаться `/health`;
4. засев и логин консолью;
5. k6;
6. для `restart` / `paused` — stop/start или pause/unpause по расписанию выше;
7. всё время раз в секунду `/health/ready` в CSV;
8. разбор консолью: таблица перцентилей и кодов, проверка лимита, `InvariantChecker`,
   события 1005 из лога — markdown для вставки в `NOTES.md`.

## Тесты

Unit-тесты в `WebApi.Tests/LoadRun/` (ссылка на `WebApi.LoadTests`) на логику, которая решает
«пройден / нет» — ошибка детектора дала бы ложный «пройден» в сдаче:

- детектор лимита: ровно 60 за 60 с; 61-й на тик раньше и на тик позже; пограничный случай;
  `429` не считаются; разные пользователи не смешиваются;
- восстановление: 1,5× на границе; 1005 ровно на 10-й секунде и через тик после.

Засев, оркестровку и сам k6 не тестируем — их проверяет реальный прогон.

## Нюансы реализации

- строки запросов k6 пишет не `--out csv`, а `console.log` с `--log-format=raw` в
  `load/out/<режим>/requests.csv` (`ep,user,start,end,status,duration`): `--out csv` даёт ~13 строк
  на запрос (все `http_req_*`), сотни мегабайт за режим; начало и конец — `Date.now()` до и после
  запроса, по ним детектор лимита. Перцентили считает консоль по этим строкам, а не
  `summaryTrendStats`: сводка k6 не умеет отбросить прогрев;
- аналитику шлют 100 синтетических админов `loadadmin001..100`: 3% смеси на пяти сидовых админах
  упёрлись бы в лимит 60 в минуту;
- админам в строках запроса ставится `user` = −1…−100, чтобы детектор не смешал их с клиентами;
- приложение запускается из `WebApi/bin/Release/net9.0` (`dotnet WebApi.dll`), а не `dotnet run`:
  `dotnet run` порождает дочерний процесс, который не гасится вместе с родителем. Строка подключения —
  выданная из `appsettings.json` с заменой базы на `club_load`, остальные параметры (пул) как в поставке;
- калибровка не нашла упора: на 1000 RPS худший p95 — 24 мс. Выше 1000 RPS 2000 пользователей дают
  больше 30 запросов в минуту на каждого и начинают упираться в лимит, так что потолок задают пул
  пользователей и лимит, а не машина. Рабочая — 70% от 1000 = 700 RPS;
- тесты `dotnet test` нельзя гонять параллельно с прогоном: `down` / `restart` / `paused` трогают
  общий Redis compose, а 700 RPS занимают соединения Postgres;
- найдено и исправлено (тест-воспроизведение → правка):
  - `running`: 14 × `500` — `53300 too many clients`: пул Npgsql по умолчанию 100, у Postgres
    `max_connections` 100 минус 3 резервных, плюс соединение `/health/ready`. В выданную строку
    подключения добавлен `Maximum Pool Size=80`; тест `ConnectionPoolTests` сверяет пул из
    `appsettings.json` со свободными слотами сервера;
  - `paused`: 801 × `500` — `TaskCanceledException` из `ScriptEvaluateAsync`: при зависшем Redis
    StackExchange.Redis сам отменяет ждущие команды, `RedisGuard` такую отмену не считал отказом.
    Теперь `OperationCanceledException` без отмены запроса — отказ Redis (1005), отмена клиентом
    по-прежнему пробрасывается; тесты `RedisGuardTests`.
