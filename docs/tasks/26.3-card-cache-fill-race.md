# 26.3 Гонка заполнения и сброса

Статус: готово (008d2c7)

Тест из [задачи 26](26-card-cache.md) на `CardCache` из 26.2.

- декоратор `ICardCache` через `StartAsync(builder => …)`: перед `FillAsync` ждёт
  `TaskCompletionSource`, затем вызывает настоящий `CardCache` — задерживается скрипт заполнения,
  а не `ICacheService.SetAsync`;
- сценарий: карточка не в кэше; чтение промахивается, читает из базы `active` с версией `n`
  и встаёт на шве; отмена `200` коммитится и пишет надгробие `n + 1`; шов отпускается, заполнение
  ничего не пишет (в hash только `v = n + 1`); первое чтение отдаёт `active` (снимок до отмены —
  контракт это разрешает), следующий запрос карточки — `cancelled`;
- второй сценарий на продвинутого: чтение его карточки задержано, чужая отмена продвигает его —
  следующий запрос показывает новый остаток;
- красный прогон — временной поломкой: удаление ключа вместо надгробия или заполнение без
  сравнения версий; вывод — в отчёт, поломка откатывается.

## Нюансы

- кода в production нет: версии в скрипте заполнения из 26.2 уже держат гонку, задача — тесты
  `GetCard_FillDelayedPastCancel_…` и `GetCard_FillDelayedPastPromotion_…` в `CardCacheTests`;
- декоратор `GatedCardCache` регистрируется через `ConfigureTestServices` над
  `ActivatorUtilities.CreateInstance<CardCache>` — последняя регистрация `ICardCache` выигрывает;
- надгробие проверяется дважды: до отпускания шва (`v = 1`, полей нет) и после заполнения;
- красный прогон: удаление ключа вместо надгробия — падает проверка до отпускания (hash пуст);
  заполнение без проверки «новее — ничего» — после отпускания в hash `v = 0` и снимок `active`.
