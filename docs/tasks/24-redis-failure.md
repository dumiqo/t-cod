# 24. Исследование: отказ Redis

Статус: готово (41a4819)

- приложение не стартует при недоступном Redis: `ConnectionMultiplexer.Connect` вызывается
  при старте;
- Redis упал во время работы: карточка должна читаться из базы. Сейчас `RedisCacheService`
  пробрасывает `RedisConnectionException`, а `ExceptionHandlingMiddleware` превращает её в `500`;
- ограничение частоты при упавшем Redis — пропускать запросы или отказывать;
- проверка готовности по задаче 6 отвечает на недоступный Redis `Degraded` (`200`) в расчёте
  на работу без него. Если решение здесь — без Redis не работать, сменить на `Unhealthy`;
- события и счётчики отказа Redis — по схеме задачи 6.

Найдено при разборе:

- сейчас Redis не использует ни один наш эндпоинт: кэша карточки нет (задача 26), ограничителя
  тоже (задача 28); идемпотентность хранится в базе;
- по умолчанию StackExchange.Redis 2.8.24 при разорванном соединении держит команды в очереди
  (`BacklogPolicy.Default`) до `AsyncTimeout`, 5 секунд: упавший Redis дал бы не `500`, а плюс
  5 секунд к каждому запросу (видно в 7.4: Ping на закрытый порт — исключение через 5 секунд);
- несработавший сброс кэша после коммита оставляет старый снимок, и тот может пережить
  перезапуск Redis: клиент после `200` на отмену видел бы `active` до конца TTL, вопреки §4;
- где хранить счётчик лимита, решает задача 27; здесь — только поведение, если он в Redis.

Решение — в заметках, раздел «Отказ Redis»: Redis вспомогательный, его отказ не роняет запросы.
Карточка читается из базы без записи в кэш; несработавший сброс не ломает операцию, ключ
запоминается в памяти экземпляра, читается мимо кэша и сбрасывается повторно; лимит при отказе
пропускает запросы; `FailFast` и предел вызова `Redis:OperationTimeout` (1 секунда); отказ —
только недоступность и тайм-аут, остальное — `500`; старт без Redis (`AbortOnConnectFail = false`);
готовность остаётся `Degraded`; событие 1004 Warning и `club.redis.failures` с тегом
`operation`. Реализация — в 26.4, лимит — в 28.2.
