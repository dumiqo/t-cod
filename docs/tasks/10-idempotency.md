# 10. Идемпотентность

Для §1 и с расчётом на §7. Тест на два одновременных запроса с одним ключом.

Ключ — в транзакции операции, после замка занятия (решение задачи 4). Тест: два одновременных
запроса с одним ключом и одним телом — оба `201` с одним и тем же телом, бронь одна. Повтор
после `503` выполняется заново, а не получает сохранённый `503`.

Повтор с тем же ключом и телом отдаёт сохранённый `201` раньше любой причины 409: иначе повтор
§1 после начала занятия получит `class-started`, а повтор §7 — `already-waiting`. В порядке
кодов (задача 2) и шкале причин (задача 3) это не записано.

Повтор по ключу — событие и `club.idempotency.replayed` (задача 6); сам ключ в лог не пишется,
только id брони. Повтор не считается списанием: `club.visits.charged` не растёт. Тест: в логе
запроса нет ключа идемпотентности (перенесено из задачи 7).

Разбита на подзадачи 10.1–10.4, каждая — свой коммит и своя строка статуса, порядок по номерам.
Механизм общий для §1 и §7; к §7 его подключает 20.4.

## 10.1 Хранение ключа и повтор

- миграция таблицы `idempotency_keys` по решению задачи 9: `user_id`, `operation`, `key_hash`
  (`sha256` от UTF-8 байт ключа), `class_id`, `seats`, снимок ответа `result_id`,
  `result_created_at`, `result_position` (nullable: строка вставляется до брони), уникальность
  по `(user_id, operation, key_hash)`; старт на чистой базе — схема меняется;
- повтор собирает тело из колонок: `status` у §1 — `active` по `operation`; тест — повтор
  отдаёт `id` и `createdAt` первого ответа точно, до микросекунды;
- ключ занимается `INSERT … ON CONFLICT DO NOTHING` в транзакции записи после замка занятия,
  тело ответа дописывается после создания брони;
- повтор с тем же ключом и телом — сохранённый `201` раньше любой причины `409`: тест — повтор
  после начала занятия даёт `201`, а не `class-started`; новой брони нет, остаток прежний;
- отказ ключ не оставляет: после `404` и `409` в хранилище ключа нет;
- длинный ключ (случайная строка больше 2704 байт) — `201`, повтор с ним отдаёт то же тело;
  ключ, отличающийся от него последним символом, — новая бронь (ключ не укорачивается);
- ключ в другом регистре — новая бронь; не-ASCII ключ `ключ` — `201`, повтор отдаёт то же тело;
- ключ одного пользователя не виден другому: тот же ключ у другого пользователя — его новая бронь.

## 10.2 Повтор по развилкам задачи 9

- тот же ключ и другое тело (`classId` или `seats`) — `409` `idempotency-key-reused`; отказ
  не оставляет следов: брони нет, остаток прежний, строка ключа не изменилась. Пары с причинами
  занятия: другое тело на начавшееся или отменённое занятие — `idempotency-key-reused`; другое
  тело с несуществующим `classId` — `404`;
- то же тело с другим форматированием JSON (порядок полей, пробелы) — повтор;
- повтор после `404` и `409`, когда причина отказа ушла, — `201` и новая бронь;
- повтор после отмены брони и после изменения её мест — снимок первого ответа: `status: active`,
  исходные `seats`; бронь в базе не меняется;
- два заголовка `Idempotency-Key` `a` и `b` — ключ `"a,b"`: повтор запроса с одним заголовком
  `a,b`;
- `idempotency-key-reused` добавить в шкалу причин 409 в заметках, первой;
- чистки ключей нет: решение задачи 9 — хранить без срока.

## 10.3 Одновременные запросы и `503`

- два одновременных запроса с одним ключом и одним телом: оба `201` с одним и тем же телом,
  бронь одна, посещения списаны один раз. Детерминированно — тест держит замок занятия,
  `[DoNotParallelize]`;
- нарушение уникальности ключа не доходит до `ExceptionHandlingMiddleware` как `500`. Замок
  занятия разводит только запросы на одно занятие: два одновременных запроса с одним ключом
  и разным `classId` берут разные замки, второй ждёт на уникальном индексе ключа и после коммита
  первого получает `23505`. Тест — на этот случай: второй получает `409`
  `idempotency-key-reused`, не `500`, бронь одна. Ключ занимается `ON CONFLICT DO NOTHING`,
  поэтому транзакция не обрывается. Обратный случай: первый откатился с `409` — второй
  выполняется как новый и получает `201`;
- повтор после `503` выполняется заново, а не получает сохранённый `503`.

## 10.4 Наблюдаемость

- повтор — событие с id брони и `club.idempotency.replayed`; `club.visits.charged`
  и `club.enrollments.created` не растут;
- ключа нет в логе ни первого запроса, ни повтора;
- тесты одновременных запросов из 10.3 дополнить: одно событие создания, один повтор.
