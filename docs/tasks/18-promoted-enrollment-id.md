# 18. Исследование: номер брони после продвижения

Статус: проработано

Когда запись из очереди становится бронью, клиент не узнаёт её id: эндпоинта со списком своих
броней или со статусом записи в очереди нет. Один из вариантов — общий id у записи в очереди
и у брони. Решить до миграции очереди. От решения зависит, можно ли кэшировать `404`
карточки — задача 25.

## Проработка

Согласованные решения; при выполнении задачи они записываются в заметки, раздел «Номер брони
после продвижения».

Факты:

- `enrollments.id` — `bigint`, `IdentityByDefaultColumn` (миграция `Initial`): у колонки своя
  последовательность, явный id при вставке Postgres принимает. Сидер id не задаёт —
  последовательность после сидов верна;
- ответ §7 отдаёт `id` записи в очереди, §8 — только `id` и `status: cancelled`, §3 о продвинутых
  ничего не отдаёт, карточка §4 ищет бронь по id;
- снимок идемпотентности §7 хранит `result_id` (раздел «Идемпотентность» заметок): повтор после
  продвижения отдаёт тот же id.

Решения:

- общий номер: запись в очереди берёт id из последовательности `enrollments.id`, продвижение
  создаёт бронь с тем же id. Клиент спрашивает `GET /enrollments/{id из §7}`: до продвижения
  `404`, после — карточка. Контракт не меняется. Не взяли: одну таблицу со статусом `waiting` —
  её пришлось бы исключать везде, где считают места (§1, §2, §3, §5, §6, сиды), а карточка
  отдавала бы `404` на `waiting`, это задевает задачи 8–17; разные номера с `enrollment_id`
  в очереди — клиент его не видит; своё поле или эндпоинт — расширение контракта, которого
  задание не просит;
- default id таблицы очереди — `nextval('enrollments_id_seq'::regclass)` в миграции
  (`HasDefaultValueSql`, пометка `// решение:`). Литерал `regclass` привязан к OID, не к имени;
  имя последовательности проверяет тест 20.1. Схема `enrollments` не меняется: отдельная общая
  последовательность потребовала бы перевесить её колонку;
- продвижение вставляет бронь с явным `Id` (пометка `// решение:`). Что EF Core / Npgsql 9
  отправляют `Id`, не равный `0`, а не генерируют свой, — допущение, его проверяет первый тест
  23.1; не подтвердится — вставка SQL;
- `createdAt` продвинутой брони — момент продвижения: время после замка в транзакции отмены или
  уменьшения мест, как у всех пишущих запросов (задача 8). Время постановки остаётся у записи
  в очереди;
- одна запись в очереди даёт не больше одной брони и при продвижении выходит из очереди
  (ограничение для задачи 21). Второе продвижение той же записи упрётся в PK `enrollments` —
  защита «посещения за бронь списываются один раз» на уровне базы, отдельный FK или `CHECK`
  не нужен;
- `404` карточки по id записи в очереди со временем становится `200`, причём продвижение идёт
  в чужом запросе (§2, §3). Рекомендация для задачи 25 — `404` не кэшировать; решается там.

Тесты — в подзадачах 20.1 и 23.1 (дописаны в их тексты).
