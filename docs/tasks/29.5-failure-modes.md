# 29.5 Отказные режимы: зависший Redis и пул соединений

Две проверки в `dotnet test`, обе — про то, как система ведёт себя при отказе зависимости. Кривая
деградации и сравнение с работающим Redis не нужны: числа зависят от машины, порога в задании
нет, решение по ним не принимается. Поведение без Redis уже измеряется в 29.3 (три режима в
`dotnet test`) и 29.4 (реальный процесс), восстановление — критерий 29.4.

## 1. Зависший Redis не должен стоить каждому запросу таймаута

Сейчас лимитер спрашивает Redis на каждом запросе, а бронь в `LocalRateJournal` снимается только
после ответа (`Release`), поэтому при зависшем Redis каждый запрос ждёт `Redis:OperationTimeout`
(по умолчанию 1 с) впустую: счётчик к этому моменту уже ведёт журнал, Redis нужен только ради
распределённости. Та же картина у кэша карточки (26.4).

- тест `[DoNotParallelize]` в `WebApi.Tests/RateLimiting/`: `TestApp.StartAsync(builder => ...)`
  с `Redis:OperationTimeout` = 200 мс и `FreezableRedisProxy` (`Freeze()`), затем 20 запросов к
  `GET /enrollments/{id}` и к `GET /schedule` — два разных потребителя Redis с разными ключами;
- ассерт детерминированный, без секундомера: число обращений к Redis считаем по событию 1005 и
  метрике `club.redis.failures` через `app.Logs` — на окно одно событие, а не 20. Если для
  точности нужен счётчик именно на уровне соединения, дописать счётчик команд в
  `FreezableRedisProxy` (это тестовая инфраструктура, TCP-прокси уже есть);
- ожидаемое поведение после правки — окно отказа: после первой неудачи лимитер и кэш не
  обращаются к Redis в течение фиксированного интервала (образец — `RedisBreakDurationSeconds`
  в чужом решении, ADR 080), интервал отсчитывается по `TimeProvider`, поэтому в тесте
  двигается `app.Clock`, а не ожиданием; константа — `// решение:` с обоснованием;
- отказ по-прежнему без `500`: `429` решает журнал, `/health/ready` — `Degraded`;
- одна правка в `RedisGuard` закрывает обе проверки (лимитер и кэш) — так и делать, отдельные
  окна на каждую ручку не нужны;
- тест на текущем коде красный — это и есть подтверждение гипотезы: правка по TDD, нюанс сюда,
  итог в заметки.
- после правки перепрогнать режим «завис» из 29.4 (`load/run.ps1 -Mode paused`) и обновить
  его строку в таблице `NOTES.md`: в 29.4 он снят до правки, с ожиданием таймаута на каждом
  запросе.

## 2. Исчерпание пула Npgsql — не `500`

`ExceptionHandlingMiddleware` превращает любое необработанное исключение в `500`, включая
`NpgsqlException` об исчерпании пула. Приёмка этого не требует, но `500` под нагрузкой читается
как дефект, а `503` + `Retry-After` — как управляемая деградация (так уже сделано для
`TransactionConflictException`).

- тест: строка подключения с `Maximum Pool Size=2` и `Timeout=1` (иначе тест ждёт 15 с), два
  соединения удерживаются `HeldLock.AcquireAsync` с открытой транзакцией, затем запрос к
  пишущему эндпоинту;
- ассерт: статус не `500`; после правки — `503` с `Retry-After` и `reason` в `ProblemDetails`,
  событие и метрика отказа по образцу `TransactionConflictFilter` (1002 и
  `club.requests.rejected`);
- восстановление в том же тесте: отпустить соединения — следующий запрос `200`, база в
  ожидаемом состоянии (отказ не оставил следов);
- проверить при проработке: как передать изменённую строку подключения через
  `TestApp.StartAsync`, и что именно бросает Npgsql 9 при исчерпании пула — по факту, а не по
  памяти;
- решение (`503` против `500`) фиксируется `// решение:` и в заметках: если решим оставить
  `500`, тест всё равно остаётся и закрепляет выбор.

## Что не проверяем

- кривую деградации, «точку перелома» и сравнение с кривой при работающем Redis — числа
  зависят от машины и не меняют решений;
- рост памяти журнала лимитера при отказе Redis — закрыто `LocalRateJournalTests`
  (`Sweep` раз в минуту удаляет пустые журналы, `TryReserve_AfterWindow_IdleUsersAreRemoved`);
- восстановление после остановки и подъёма Redis под нагрузкой — критерий 29.4.

## Нюанс для заметок

`LocalRateJournal` считает в пределах процесса: при отказе Redis лимит 60 в минуту действует
на инстанс, то есть N инстансов дадут 60×N. Прогон 29.4 идёт на одном процессе, поэтому в
отчёте это ограничение надо назвать явно, а не выдавать за распределённый лимит.
