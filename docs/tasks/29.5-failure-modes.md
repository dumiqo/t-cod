# 29.5 Отказные режимы: зависший Redis и пул соединений

Две проверки в `dotnet test`, обе — про то, как система ведёт себя при отказе зависимости. Кривая
деградации и сравнение с работающим Redis не нужны: числа зависят от машины, порога в задании
нет, решение по ним не принимается. Поведение без Redis уже измеряется в 29.3 (три режима в
`dotnet test`) и 29.4 (реальный процесс), восстановление — критерий 29.4.

## 1. Зависший Redis не должен стоить каждому запросу таймаута

Сейчас `RedisGuard.TryAsync` ходит в Redis на каждом вызове, поэтому при зависшем Redis каждый
запрос ждёт `Redis:OperationTimeout` (по умолчанию 1 с) на каждую операцию впустую: лимит к
этому моменту уже решил `LocalRateJournal`, карточка читается из БД.

Потребители Redis (проверено по коду): `rate-limit` (`RateLimitMiddleware`, весь
`ClubApiController` под `[RateLimited]`) и кэш карточки — `cache-get`, `cache-set`,
`cache-remove`. У `GET /schedule` своего потребителя нет — только `rate-limit`, поэтому тест
идёт через `GET /enrollments/{id}`: он задевает `rate-limit` и `cache-get`.

### Решения

- **окно отказа открывает только `TimeoutException`** (в том числе `RedisTimeoutException`).
  `RedisConnectionException` окно не открывает: быстрый отказ ничего не стоит, дорого только
  ожидание. Заодно не меняются существующие тесты с `BreakRedis` / `RestoreRedis` (событие на
  каждый запрос, обращение к Redis сразу после восстановления) — `// решение:`;
- **окно на операцию** (`rate-limit`, `cache-get`, `cache-set`, `cache-remove`), но правка одна —
  в `RedisGuard`. Глобальное окно сломало бы `GetCard_RedisHung_...`, который ждёт в одном
  запросе два таймаута; по операциям за окно — не больше одного ожидания на операцию;
- **длительность — 5 с**, константа в `RedisGuard` с `// решение:`: после `unpause`
  восстановление не дольше 5 с, укладывается в 10-секундный критерий 29.4; цена — один таймаут
  на операцию раз в 5 с. Отсчёт по `TimeProvider`, в тестах двигается `app.Clock`;
- **одна проба**: первый вызов после истечения окна через `CompareExchange` продлевает окно и
  пробует сам, остальные пропускают Redis. Успех закрывает окно, неудача оставляет ещё на 5 с.
  Иначе под нагрузкой в момент истечения все одновременные запросы ждали бы таймаут;
- **пропуск тихий**: пока окно открыто, `TryAsync` сразу возвращает `false` без события 1005 и
  без `club.redis.failures`; новых событий («окно открыто/закрыто») нет. Вызывающий код ведёт
  себя как при неудаче: журнал лимитера (бронь остаётся), карточка из БД, надгробие уходит в
  `_pending` — устаревших чтений нет;
- `/health/ready` ходит в Redis напрямую (`RedisReadinessCheck`), окно его не касается —
  `Degraded`, как и раньше. Отказ по-прежнему без `500`.

### Тесты

`WebApi.Tests/Redis/`, `[DoNotParallelize]`, `TestApp.StartAsync(builder => ...)` с
`Redis:OperationTimeout` = 200 мс и `FreezableRedisProxy`. Ассерты по событию 1005 и метрике
`club.redis.failures` через `app.Logs`, без секундомера.

- 20 запросов `GET /enrollments/{id}` после `Freeze()` → все `200` с карточкой из БД, ровно одно
  событие 1005 `rate-limit` и одно `cache-get`, оба `TimeoutException`; на текущем коде — 20 и 20
  (красный — подтверждение гипотезы);
- граница окна: `app.Clock` на 5 с минус тик → запрос без новых событий; ещё тик → ровно одна
  проба на операцию;
- одновременные запросы в момент истечения окна → одна проба на операцию (по событиям);
- восстановление: дописать `Unfreeze()` в `FreezableRedisProxy` (тестовая инфраструктура),
  сдвинуть часы на окно → проба успешна, следующие запросы снова пишут в Redis (карточка
  появилась в хеше `card:{userId}`), новых 1005 нет;
- `/health/ready` при зависшем Redis — `Degraded`.

После правки перепрогнать режим «завис» из 29.4 (`load/run.ps1 -Mode paused`) и обновить его
строку в таблице `NOTES.md`: в 29.4 он снят до правки, с ожиданием таймаута на каждом запросе.

## 2. Исчерпание пула Npgsql — не `500`

`ExceptionHandlingMiddleware` превращает любое необработанное исключение в `500`, включая
исключение Npgsql об исчерпании пула. Приёмка этого не требует, но `500` под нагрузкой читается
как дефект, а `503` + `Retry-After` — как управляемая деградация (так уже сделано для
`TransactionConflictException`).

### Решения

- **`503`** + `Retry-After: 1` + `reason` = `"database-unavailable"` в `ProblemDetails`,
  `// решение:` и строка в заметках;
- **признак**: `NpgsqlException` с `InnerException is TimeoutException` — исчерпание пула,
  таймаут подключения к лежащей БД, таймаут команды: всё это «БД сейчас не отвечает». Текст
  сообщения не проверяем — хрупко. Точный тип у Npgsql 9 подтверждается красным тестом, а не
  по памяти;
- **где**: новый глобальный MVC-фильтр `DatabaseUnavailableFilter` рядом с
  `TransactionConflictFilter`. Middleware до MVC в БД не ходят (`RateLimitMiddleware`, JWT),
  поэтому фильтр покрывает всё. В отличие от `TransactionConflictFilter` — без
  `long.Parse(...NameIdentifier!)`: userId в событии nullable, анонимный логин тоже под фильтром;
- **событие 1006** (следующий свободный номер), операция = имя action, метрика
  `club.requests.rejected` с `reason`;
- **безопасность повтора — известное ограничение**: если таймаут случится на чтении после
  коммита (запрос открывает соединение второй раз), запись уже прошла, а `Retry-After`
  обещает безопасный повтор. Принимаем: повтор упрётся в `409` или ключ идемпотентности.
  При реализации найти пишущие эндпоинты с чтением после коммита и назвать их в заметках.

### Тесты

- строка `app.ConnectionString + ";Maximum Pool Size=2;Timeout=1"` передаётся через
  `StartAsync(builder => builder.ConfigureAppConfiguration(...))` — регистрация позже фабрики и
  перекрывает её (проверить при реализации). Логин — до захвата пула;
- два `HeldLock.AcquireAsync` с той же строкой (пул Npgsql привязан к строке подключения —
  соединения берутся из пула приложения; хватает `SELECT 1` в открытой транзакции), затем
  `POST /enrollments` → `503`, `reason` = `"database-unavailable"`, `Retry-After: 1`, событие
  1006, метрика; в БД нет записи, абонемент не списан;
- восстановление в том же тесте: отпустить соединения → тот же запрос `201`, состояние БД
  верное;
- негатив: другая ошибка Npgsql (не таймаут) остаётся `500` без события 1006.

## Что не проверяем

- кривую деградации, «точку перелома» и сравнение с кривой при работающем Redis — числа
  зависят от машины и не меняют решений;
- рост памяти журнала лимитера при отказе Redis — закрыто `LocalRateJournalTests`
  (`Sweep` раз в минуту удаляет пустые журналы, `TryReserve_AfterWindow_IdleUsersAreRemoved`);
- восстановление после остановки и подъёма Redis под нагрузкой — критерий 29.4.

## Нюанс для заметок

`LocalRateJournal` считает в пределах процесса: при отказе Redis лимит 60 в минуту действует
на инстанс, то есть N инстансов дадут 60×N. Прогон 29.4 идёт на одном процессе, поэтому в
отчёте это ограничение надо назвать явно, а не выдавать за распределённый лимит.

## Нюансы реализации

- EF Core 9 при исчерпании пула бросает не `NpgsqlException`, а `InvalidOperationException`
  («likely due to a transient failure») с `NpgsqlException` → `TimeoutException` внутри —
  выяснено красным тестом; фильтр смотрит на исключение и на одну обёртку.
- `FreezableRedisProxy.Freeze()` теперь не выбрасывает байты, а держит их до `Unfreeze()`, как
  `docker pause`: иначе после «отпускания» ответы StackExchange.Redis разошлись бы с командами.
- Пишущих эндпоинтов с чтением после коммита нет: после транзакции только сброс кэша в Redis.
  Остаточный риск — тайм-аут на самом `COMMIT` (в заметках, «База не отвечает»).
