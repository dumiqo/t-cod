# 20.1 Таблица очереди и постановка (§7)

Статус: готово (26ca785)

- миграция таблицы очереди (id по решению задачи 18, уникальность по решению задачи 19); сиды
  не меняются; старт на чистой базе — схема меняется;
- id записи в очереди — из последовательности `enrollments.id` (задача 18): id из ответа §7
  не совпадает ни с одной бронью, следующая запись (§1) получает id больше него;
- эндпоинт, транзакция, замок занятия — первое чтение;
- коды подзадачи — только `201`, `400`, `401`, `404` (занятия нет). Причин `409` здесь нет:
  ловушку «отменённое занятие даёт `404` без `IgnoreQueryFilters()`» ловит тест
  `class-cancelled` в 20.2;
- данные тестов `201`: занятие заполнено так, что свободных мест меньше запрошенного, — иначе
  тесты упадут, когда 20.2 добавит `seats-available`. Помощник «полное занятие» заводится здесь;
- `Idempotency-Key` до 20.4 обязателен, но не сохраняется. Тесты — только `400` по образцу §1:
  нет заголовка, `""`, `" "`, `"\t"`; нет ключа и неверные `seats` — обе ошибки. Что повторный
  ключ даёт вторую запись, не закрепляется: это временное поведение, 20.4 его меняет;
- `201`: тело с точными значениями, `createdAt` усечён до микросекунд; `position` считается
  среди ожидающих; в базе — запись очереди, места и остаток прежние;
- порядок очереди — по решению задачи 19 (варианты — в [задаче 20](20-waitlist-join-leave.md));
- тест репозитория (`TestDb.CloneAsync()`) — только подсчёт `position`. «Есть ли своя
  `waiting`» — в 20.2, «своя запись по id без отслеживания» — в 20.3: метод появляется вместе
  с потребителем;
- частичный уникальный индекс есть: вторая `waiting` того же клиента на то же занятие — `23505`,
  записи `cancelled` и `promoted` вставке не мешают.

По решению задачи 19:

- таблица `waitlist_entries`: `id` (default `nextval('enrollments_id_seq'::regclass)`),
  `class_id` и `user_id` с FK, `seats` (`CHECK seats >= 1`), `status` (`CHECK` по `waiting`,
  `cancelled`, `promoted`), `created_at`, `cancelled_at` (nullable); частичные индексы
  `(class_id, id)` и уникальный `(class_id, user_id)`, оба `WHERE status = 'waiting'`;
- тест на имя последовательности и на её `cache_size = 1`: монотонность id между сессиями,
  на которой держится порядок;
- `position` — число записей `waiting` того же занятия с `id ≤` своего: тест — три постановки
  дают позиции 1, 2, 3; запись `cancelled` или `promoted` впереди позицию не занимает; записи
  другого занятия не считаются;
- `created_at` — время после замка, усечено до микросекунд; порядок — по `id`, пометка
  `// решение:`.

Нюансы при выполнении:

- проверено: с `HasDefaultValueSql` Npgsql `IDENTITY` не ставит — миграция
  `AddWaitlistEntries` содержит только `defaultValueSql`; закрепляет тест
  `Id_DefaultsToEnrollmentsSequence` (`is_identity = NO`);
- FK — `ON DELETE CASCADE`, как у `enrollments` (удаление по соглашению EF); FK-индекс
  `class_id` объявлен явно по той же причине, что в `EnrollmentConfiguration`;
- тесты `400` проходят без особого кода: валидация — атрибутами `JoinWaitlistRequest`
  и `[Required]` у заголовка, как в §1.
