# 29.5 Crash-тест без кэша

Тем же инструментом, что 29.4 (NBomber): сколько система выдерживает без Redis и как восстанавливается.
Тоже вручную, итог — в заметки.

- нагрузка наращивается ступенями при остановленном Redis до деградации: фиксируем точку
  перелома (рост p95, появление `503`), сравниваем с той же кривой при работающем Redis;
- деградация должна быть управляемой: `503` с `Retry-After` (тайм-аут блокировки) или `429`,
  а не `500` и не падение процесса;
- после снятия нагрузки — восстановление: задержки возвращаются к исходным, процесс жив,
  `/health/ready` отвечает, инварианты из 29.3 выполняются;
- гипотезы, что проверить (не подтверждены):
  - исчерпание пула соединений Npgsql под нагрузкой даёт исключение, которое
    `ExceptionHandlingMiddleware` превратит в `500`, а не `503`;
  - журнал лимитера в памяти (`LocalRateJournal`) при упавшем Redis растёт с числом
    пользователей — проверить, что старые записи вычищаются и память не растёт без предела;
  - зависший Redis (`docker pause`) под нагрузкой: каждый запрос ждёт `Redis:OperationTimeout`,
    не съедает ли это пул потоков или соединений с базой;
- подтвердившаяся гипотеза — отдельная правка по TDD: тест-воспроизведение в `dotnet test`,
  затем исправление; решение (например, `503` при исчерпании пула) — `// решение:` и заметки.
