# 26. Кэш карточки

Статус: проработано

С поведением при отказе Redis по итогам задачи 24. Какие операции сбрасывают кэш и как —
по решению задачи 25.

Тест на гонку заполнения и сброса из задачи 25: чтение промахивается и читает базу, его
заполнение кэша задерживается, пока отмена не закоммитится и не запишет надгробие; заполнение
ничего не пишет, и следующий запрос карточки показывает `cancelled`.

Разбита на подзадачи 26.1–26.4, каждая — свой коммит и своя строка статуса, порядок по номерам.
26.1–26.3 зависят только от задачи 25, 26.4 — от задачи 24 и от `CardCache` из 26.2.

## Проработка

Факты:

- версия поднимается там, где абонемент уже заблокирован: §1 — `EnrollInTransactionAsync`
  (`LockByUserAsync`), §3 и §2 — свои `RunAsync` (`LockByUsersAsync` с ожидающими), продвижение —
  `PromoteAsync`, абонементы продвинутых уже в `passes` под замком;
- свойство в сущность уже добавлялось (`Enrollment` в 12.1): `Pass.Version` — так же,
  с миграцией и настройкой в `PassConfiguration`;
- §2 отдаёт карточку, прочитанную под замками `GetCardAsync` (задача 14), — она не меняется;
- `KeyPrefixedConnection` префиксует ключи через `WithKeyPrefix` на `GetDatabase`;
- настройки со значением по умолчанию и проверкой при старте уже есть: `TransactionSettings`
  (`BindConfiguration`, `Validate`, `ValidateOnStart`) — `Cache:CardTtl` и `Redis:OperationTimeout`
  делаются так же.

Решения:

- **Подъём версии** — ровно `+1` на каждого затронутого пользователя за операцию, даже если у него
  продвинуто несколько записей. Номер наружу не выходит, значим только порядок; тесты сверяют точное
  значение (`0 → 1`).
- **Чтение с версией** — новый метод репозитория `GetVersionedCardAsync` →
  `VersionedCard(EnrollmentCard Card, long Version)` тем же одним SELECT. `GetCardAsync` остаётся
  для ответа §2, `EnrollmentCard` не меняется: версия снимка лежит в поле `v` hash.
- **Снимок** — JSON `EnrollmentCard` через `System.Text.Json` с настройками по умолчанию. Тест:
  тело ответа при попадании побайтно совпадает с телом при промахе (`createdAt`, `startsAt` в UTC
  с `Z`, `validUntil`). Битый JSON в поле — `500` (задача 24).
- **Где пишутся надгробия** — в `EnrollmentService` после коммита: сначала события и счётчики
  операции, как сейчас, затем надгробия. Результаты `EnrollResult.Created`,
  `CancelResult.Cancelled`, `ChangeSeatsResult.Changed` несут новые версии затронутых
  пользователей (`userId → version`).
- **Несколько пользователей** — один вызов скрипта на пользователя, последовательно. При отказе
  (26.4) ясно, какой ключ запомнить. Худший случай при «зависшем» Redis — N ×
  `Redis:OperationTimeout`, N — автор и продвинутые.
- **Шов для теста гонки** — интерфейс `ICardCache`. Тест через `StartAsync(builder => …)`
  регистрирует декоратор над настоящим `CardCache`: перед `FillAsync` он ждёт `TaskCompletionSource`,
  затем вызывает настоящее заполнение с прочитанной раньше версией. Production-код о тестах
  не знает, скрипт исполняется настоящий.
- **Событие `connect`** (26.4): с `AbortOnConnectFail = false` `Connect` не бросает. Если после
  `Connect` нет соединения (`IsConnected`), пишется 1004 `connect` без исключения, причина —
  в тексте; исключение с причиной даст первый `cache-get`.
- **Повтор несработавших надгробий** (26.4): в памяти `userId → версия` (максимальная). Перед
  каждой операцией `CardCache` (чтение, заполнение, надгробие) повторяются все ожидающие сбросы.
  Первый отказ прерывает повтор, и текущая операция считается отказом. Карточка ожидающего
  пользователя читается из базы и в кэш не пишется.
