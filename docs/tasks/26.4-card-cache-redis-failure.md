# 26.4 Кэш при отказе Redis

Статус: проработано

Поведение — по решению задачи 24 (заметки, раздел «Отказ Redis») и проработке
[задачи 26](26-card-cache.md). Здесь же делается общая часть, которую потом использует 28.2.

- «страж» вызова Redis — своя обёртка: предел `Redis:OperationTimeout` (по умолчанию
  `00:00:01`, проверка при старте 1 мс ≤ x < 5 с, как у `Transactions:LockTimeout`), отказом
  считаются только `RedisConnectionException`, `RedisTimeoutException` и свой тайм-аут;
  `RedisServerException`, `JsonException` — `500`; отмена по токену запроса пробрасывается;
- подключение: `AbortOnConnectFail = false` и `BacklogPolicy.FailFast` — приложение стартует
  без Redis, при разорванном соединении отказ мгновенный. Механизм предела (`AsyncTimeout`
  или `WaitAsync`) — проверить до кода: у `AsyncTimeout` точность может быть не лучше
  интервала проверки клиента;
- старт без соединения (`IsConnected` ложно после `Connect`) — событие 1005 `connect` без
  исключения, причина в тексте; исключение даст первый `cache-get`;
- карточка: чтение из кэша упало — читается из базы, `200`, в кэш не кладётся;
- сброс упал после коммита — операция отвечает обычным успехом; в памяти экземпляра
  (в `CardCache` из 26.2, выданный `RedisCacheService` не меняется) запоминается
  `userId → версия` надгробия, максимальная. Карточка такого пользователя читается из базы
  и в кэш не пишется. Перед каждой операцией `CardCache` (чтение, заполнение, надгробие)
  повторяются все ожидающие надгробия; после успеха пользователь забывается, первый отказ
  прерывает повтор, и текущая операция считается отказом;
- надгробия нескольким пользователям (отмена с продвижением) — по одному вызову,
  последовательно: отказ одного не мешает попытке следующего, запоминается каждый упавший.
  Худший случай при «зависшем» Redis — N × `Redis:OperationTimeout`;
- событие 1005 Warning с исключением и тегом `operation` (`connect`, `cache-get`, `cache-set`,
  `cache-remove`) и счётчик `club.redis.failures` с тем же тегом на каждый отказ;
  `club.requests.rejected` не меняется;
- тесты ломают Redis настоящим клиентом, без поддельных исключений:
  - недоступен со старта — мультиплексор на закрытый порт через `StartAsync(builder => …)`:
    приложение стартует, карточка `200` из базы, событие `connect`;
  - «завис» — «молчащий» `TcpListener`, как в тестах готовности 7.4: ответ не позже предела;
  - упал во время работы — переключатель `app.BreakRedis()` / `app.RestoreRedis()`
    в `KeyPrefixedConnection`: на время отдаёт базу мультиплексора на закрытом порту, общий Redis
    тестов не трогается. Сценарий: карточка закэширована, Redis сломан, отмена `200`, Redis
    вернулся — карточка `cancelled`; то же с продвинутым;
- готовность не меняется: `Degraded` (`200`), тесты 7.4 остаются как есть.

## Нюансы

- событие отказа Redis — **1005** `RedisFailure`, а не 1004: 1004 уже занят `IdempotentReplay`
  (задача 10). Заметки и 28.2 исправлены;
- «страж» — `WebApi/Redis/RedisGuard.TryAsync(operation, call, ct)`: `WaitAsync(OperationTimeout, ct)`,
  отказ — `RedisConnectionException` и `TimeoutException` (в том числе `RedisTimeoutException`);
  `AsyncTimeout` не взят — тайм-ауты клиент проверяет в heartbeat, точность около секунды;
- подключение — `RedisConnection.Connect` (`AbortOnConnectFail = false`, `FailFast`), им же
  пользуются тесты; событие `connect` пишет `RedisGuard.ReportStart` после создания
  мультиплексора, причина — в `Reason`. Счётчик `connect` тестом не проверен: `MetricCollector`
  `TestApp` создаётся после старта хоста;
- «молчащий» `TcpListener` из 7.4 с `FailFast` даёт мгновенный отказ, а не тайм-аут: без ответа
  на рукопожатие соединения нет. «Завис» поэтому — свой прокси `FreezableRedisProxy` к настоящему
  Redis: рукопожатие проходит, после `Freeze()` ответы не доходят. Тест: ответ `200` из базы за
  ≥ 190 мс и < 1,2 с при пределе 200 мс, отказ `cache-get` с `TimeoutException`;
- `ICardCache.GetAsync` отдаёт `(Available, Card)`: при `Available = false` карточка читается
  из базы и `FillAsync` не вызывается. `GetAsync` и `FillAsync` принимают токен запроса;
  `InvalidateAsync` — нет: сброс после коммита отменой клиента не теряется;
- повтор ожидающих: упавший повтор пишет своё событие `cache-remove`, текущая операция
  отдельного события не пишет — вызова не было. Поэтому при отмене с продвижением во время отказа
  два события `cache-remove`: автор и повтор автора перед продвинутым; запомнены оба;
- удаление из ожидающих — `TryRemove(userId, version)`: если за время повтора упал более новый
  сброс того же пользователя, его версия не теряется;
- `RedisServerException` (`WRONGTYPE`) и битый JSON — `500` без события 1005, тестами закреплено.
