# 16. Расписание (§5)

Статус: проработано

- страницы, `freeSeats`, `mySeats`, индексы под сотни тысяч занятий;
- `EnrollmentRepository.GetByUserAsync` загружает все брони пользователя — для `mySeats`
  не подходит.

Разбита на подзадачи 16.1–16.4, каждая — свой коммит и своя строка статуса, порядок по номерам.
Токен — по решению задачи 15. Подзадачи наблюдаемости нет: своих событий и счётчиков
у расписания нет (задача 15).

Решено при разборе (вопросы и ответы до кода), общее для подзадач:

- от задач 10–14 не зависит: нужен только статус брони `active`. `EnrollmentStatuses.Active` —
  `const`, в SQL уходит литералом, и предикат частичного индекса с ним совпадает. Часы
  расписание не читает: в выборку попадают и прошедшие занятия, контракт фильтрует только
  по периоду. Админ видит то же, что клиент;
- файлы — `WebApi/Schedule/`: `ScheduleController` (`[ApiController] [Route("schedule")]`,
  наследник `ClubApiController`); `ScheduleService` — запрос страницы, отрезание `limit + 1`,
  следующий токен; `ContinuationToken` (`Encode` / `TryDecode`) и `ContinuationTokenModelBinder`;
  ответы `ScheduleResponse(Items, ContinuationToken)`, `ScheduleItemResponse(ClassId, Title,
  StartsAt, DurationMinutes, Room, Capacity, FreeSeats, MySeats)`, `ScheduleRoomResponse(Id,
  Name)`. `continuationToken: null` сериализуется, а не опускается;
- запрос к базе — `IClassRepository.GetSchedulePageAsync(ScheduleQuery query, long userId, ct)`
  → `List<ScheduleRow>`. `ScheduleQuery` (уже округлённые `From` и `To`, `RoomId`, курсор
  `(StartsAt, Id)` или его нет, `Take`) и `ScheduleRow` (поля занятия, имя зала, суммы мест
  в `long`) — в `DataAccessLayer`;
- один SQL на страницу: фильтр по периоду и залу (фильтр `!IsCancelled` — глобальный), курсор
  сравнением строк `EF.Functions.GreaterThan((c.StartsAt, c.Id), (at, id))` (есть в Npgsql EF
  9.0.4, `ITuple`), коррелированные `Sum((long)e.Seats)` по активным броням занятия и по активным
  броням пользователя, `c.Room.Name`, `OrderBy(StartsAt).ThenBy(Id).Take(take)`. Сравнение
  строк, а не `a > x OR (a = x AND id > y)`: по нему Postgres гарантированно ведёт индекс
  `(starts_at, id)`. Ограничение и приведение к `int` — в C#;
- `freeSeats = max(0, capacity − занято)` — не больше `capacity`, в `int` помещается.
  `mySeats = min(сумма, int.MaxValue)`, пометка `// решение:`: через API сумма не больше
  вместимости, переполнение возможно только при правке базы мимо API, а `500` на всю страницу
  чтения из-за одного испорченного занятия хуже насыщения;
- привязка: `from`/`to` — `UtcDateTimeModelBinder` из 7.3; `long? roomId`; `[Range(1, 100)] int?
  limit`, затем `?? 20` — на `int limit = 20` пустое `?limit=` дало бы `400`, а по решению
  задачи 2 пустое значение — то же, что отсутствующее; `continuationToken` — свой binder, пустое
  значение — токена нет. `roomId` `0`, `-1` и несуществующий зал — пустой список; `abc`
  и переполнение `long` — `400` от привязки. Тексты ошибок привязки стандартные;
- `to > from` сверяется по сырым значениям, до округления: так в контракте. Только если обе
  даты разобрались; ошибка — `ModelState.AddModelError("to", "The to field must be later than

- сверка токена с query — только если `from`, `to` и токен разобрались: ключ
  `continuationToken`, текст `The continuationToken does not match from, to and roomId.`
  Неразбираемый токен — стандартный `The value '…' is not valid for continuationToken.` Все
  ошибки запроса — в одном `400`, в том числе несовпадение токена вместе с `to ≤ from`;
- тесты — `WebApi.Tests/Schedule/`: `ScheduleTests` (16.1), `ScheduleSeatsTests` (16.2),

## 16.1 Параметры и выборка

Статус: проработано

- эндпоинт на `ClubApiController`, `from`/`to` через binder'ы из 7.3;
- `400` по таблице контракта: нет `from` или `to`, неверный формат дат и `roomId`, `limit` `0`,
  `101` и нечисловой, `to` равен `from` и раньше; `401`;
- границы периода: `startsAt` равен `from` — входит, равен `to` — нет, на тик раньше `to` —
  входит; смещение во входе приводится к UTC;
- ловушка: Npgsql отбрасывает доли меньше микросекунды у параметра, поэтому `from` и `to`
  округляются вверх до микросекунды (`CeilingToMicroseconds`, `// решение:` у вызова). Тесты:
  `startsAt = from − 1 тик` при `from` с тиком сверх микросекунды — не входит,
  `startsAt = to − 1 тик` — входит; юнит на округление: `.0000001` → `.000001`, ровная
  микросекунда не меняется, `DateTime.MaxValue` не переполняется;
- порядок `(starts_at, id)` — по решению задачи 15;
- отменённые занятия не попадают; фильтр по несуществующему залу — пустой список;
- порядок по `startsAt`; `limit` по умолчанию 20, `1` и `100`.

Решено при разборе:

- минимальный код: эндпоинт, привязка, `to > from`, округление, `GetSchedulePageAsync` без
  курсора с `Take = limit`; `freeSeats = capacity`, `mySeats = 0`, `continuationToken = null`.
  Суммы — в 16.2, `limit + 1` и токен — в 16.3;
- `CeilingToMicroseconds` — рядом с `TruncateToMicroseconds` в `WebApi/Time/TimeExtensions.cs`.
  `DateTime.MaxValue` остаётся `DateTime.MaxValue`: переключатель бесконечностей Npgsql в проекте
  не выключен, `MaxValue` уходит в базу как `infinity`, и граница `starts_at < to` верна;
- тесты создают свой зал и занятия в далёком периоде, где нет сидов (за год после
  `app.SeededAt`), без броней — поэтому тело ответа сравнивается целиком и точно:
  `freeSeats = capacity`, `mySeats = 0`, `continuationToken: null` при `limit` не меньше числа
  занятий. Тест 16.1 с большим числом занятий, чем `limit`, токен не утверждает — он появится
  в 16.3;
- positive: несколько занятий в двух залах — полное тело, порядок по `startsAt`; фильтр
  по залу — только его занятия; `limit` по умолчанию — 20 из 21 занятия; `limit` `1` и `100`;
- negative: `400` — нет `from`, нет `to`, `?from=`, неверный формат `from` и `to` (пробел вместо
  `T`, дата-время в неверном виде), `roomId` `abc` и больше `long`, `limit` `0`, `101`, `abc`,
  `to` равен `from`, `to` раньше `from`; ключ и текст ошибки — точные; несколько неверных
  параметров — все ошибки в одном `400`. `401` без токена. Отменённое занятие в периоде
  не попадает;
- corner: границы периода выше (равенство `from`, равенство `to`, тик до `to`, тик до `from`
  при `from` с тиком сверх микросекунды); `from` со смещением `+03:00` — те же занятия, что
  в UTC; `from = …:00.0000001`, `to = …:00.0000002` — `200`, пустой `items`; `to =
  9999-12-31T23:59:59.9999999Z` — занятия периода на месте; `?roomId=&limit=` — как без них;
  `roomId` `0`, `-1` и несуществующий — `{"items":[],"continuationToken":null}`; два занятия
  с одинаковым `startsAt` — по возрастанию `id`;
- репозиторий: отменённые не попадают, фильтр по залу, период `[from, to)` на значениях
  с микросекундами, порядок `(starts_at, id)`, `Take`;
- `NOTES.md`, «Расписание»: границы периода, округление вверх и почему, `to > from` по сырым
  значениям.

Найдено при выполнении:

- `to > from` не может стоять в теле действия: `[ApiController]` отвечает `400` до действия,
  и при неверном `limit` ошибка `to` терялась бы. Проверка — в `OnActionExecuting` контроллера
  (`ScheduleController : IActionFilter`, такой фильтр MVC вызывает раньше `ModelStateInvalidFilter`);
  `ActionArguments` содержит только разобранные значения — «только если обе даты разобрались»
  выполняется само. Сверку токена в 16.3 — туда же, по той же причине. Методы фильтра —
  явной реализацией интерфейса: публичные MVC считает действиями, и `/swagger` отвечал `500`
  (поймал `StartupTests.Swagger_ServesDocument`);
- стандартный текст ошибки привязки у `long?` / `int?` — `The value 'abc' is not valid.`
  (без `for <имя>`), в отличие от наших binder'ов дат;
- `userId` в `GetSchedulePageAsync` и суммы в `ScheduleRow` не добавлены — появятся в 16.2.

## 16.2 `freeSeats` и `mySeats`

Статус: проработано

- `freeSeats` — вместимость минус места активных броней, отменённые брони не считаются;
  переполненное занятие — `0`, не меньше;
- `mySeats` — сумма мест активных броней текущего пользователя, несколько броней на одно
  занятие складываются; чужие и отменённые не считаются; без броней — `0`;
- одним запросом на страницу, без загрузки всех броней пользователя.

Решено при разборе:

- коррелированные суммы в `GetSchedulePageAsync`, ограничение `freeSeats` снизу нулём
  и насыщение `mySeats` (с `// решение:`) — в `ScheduleService` или при сборке ответа;
- positive: засеянная база, `user001`, первая страница периода сидов с `limit 100` — у каждого
  занятия `freeSeats` и `mySeats` равны значениям, посчитанным тестом из свежего `DbContext`
  (в сидах есть занятия, заполненные до 0, 1 и 2 свободных мест — `freeSeatsTargets`). На своих
  данных: две брони пользователя на одном занятии складываются в `mySeats`;
- negative: чужие брони не входят в `mySeats`, но входят в занятые; отменённые брони — ни туда,
  ни туда;
- corner: занятие без броней — `freeSeats = capacity`, `mySeats = 0`; переполненное занятие
  (брони больше вместимости, внесены в базу) — `freeSeats = 0`; две брони пользователя
  по `int.MaxValue`, внесённые в базу, — `mySeats = int.MaxValue`, `freeSeats = 0`;
- один SQL: хост теста включает `Microsoft.EntityFrameworkCore.Database.Command` на Information,
  у пользователя сто броней на других занятиях — за запрос расписания ровно одно событие
  `CommandExecuted`. Что тест ловит регрессию — проверить поломкой: временный вызов
  `GetByUserAsync` или отдельный запрос сумм;
- репозиторий: суммы в `long` без переполнения, `Sum` по пустому набору — `0`.

## 16.3 Страницы и токен

Статус: проработано

- обход всех страниц даёт каждое занятие ровно один раз, в том числе занятия с одинаковым
  `startsAt` на границе страницы (в сидах 4 пары, видны 3 — занятие 39 отменено; пару на границе
  тест создаёт сам);
- обход засеянной базы: последовательность `classId` совпадает с выборкой неотменённых занятий
  из свежего `DbContext` по `(starts_at, id)`;
- последняя страница — `continuationToken: null`; страница ровно на `limit` занятий; пустой
  `?continuationToken=` — первая страница;
- токен — по задаче 15: двоичный, версия `1`, `from`/`to`/`roomId` и курсор, base64url без `=`;
  разбор — чистый класс с юнит-тестами и binder, ошибка под ключом `continuationToken`;
- `400` на каждый признак «не разбирается» (алфавит, длина, версия, признак `roomId`, тики вне
  `DateTime`) и на несовпадение `from`, `to`, `roomId` после нормализации — сверка в действии,
  тот же `ValidationProblem`; смена `limit` между страницами — продолжение без ошибки;
  `2026-01-01` и `2026-01-01T03:00+03:00` в `from` — одни и те же параметры.

Решено при разборе:

- `Take = limit + 1`, курсор в `ScheduleQuery`, `ContinuationToken` и binder, сверка в действии,
  `// решение:` у `ThenBy` и у сверки (по задаче 15);
- обход засеянной базы и лимит частоты (задача 28, 60 запросов в минуту): весь период сидов
  обходится с `limit` 7 и 100; с `limit` 1 и 2 — подпериод примерно на 40 занятий, в который
  входит пара 79–80 с одинаковым `startsAt`. Иначе обход с `limit` 1 (185 запросов) и 2
  (93 запроса) упадёт после задачи 28;
- positive: обходы выше; пара с одинаковым `startsAt` ровно на границе страницы — своими данными;
  страница ровно на `limit` занятий — следующая пустая не нужна, токен `null`; смена `limit`
  между страницами; `2026-01-01` и `2026-01-01T03:00+03:00` в `from` — продолжение;
- negative: один интеграционный `400` на неразбираемый токен; несовпадение `from`, `to`, `roomId`
  (в том числе токен с залом при запросе без зала и наоборот) — `400`; токен из пробелов —
  `400`; плохой токен вместе с `to ≤ from` — обе ошибки в одном `400`;
- corner (из курсора по значениям, задача 15): занятие, на котором кончилась страница, между
  запросами отменили — следующая страница начинается со следующего занятия, без пропуска
  и повтора; занятие впереди курсора отменили — не придёт; новое занятие позади курсора —
  не придёт; токен пользователя A у пользователя B — продолжение работает, `mySeats` посчитан
  для B. Строку «не снимок» в заметках тесты не заменяют, а закрепляют;
- юниты `ContinuationTokenTests`: круг `Encode` → `TryDecode` с залом и без; в строке нет `=`,
  `+`, `/`; каждый признак «не разбирается» — символ не из алфавита (`+`, `/`, `=`), длина
  не та для признака `roomId`, версия не `1`, признак не `0`/`1`, тики вне `DateTime`;
- репозиторий: курсор при равном `startsAt` — строго после `id`, `Take` отдаёт `limit + 1`;
- `NOTES.md`, «Расписание»: страницы, токен, «не снимок»; задача 15 — `готово`.

## 16.4 Индексы

Статус: проработано

- миграция индексов под выборку по периоду и залу и под суммы мест; старт на чистой базе;
- план запроса на синтетической базе — ручная проверка, вывод `EXPLAIN` в заметки.

Решено при разборе:

- индексы: `IX_classes_starts_at_id` — `classes (starts_at, id) WHERE NOT is_cancelled`;
  `IX_classes_room_id_starts_at_id` — `classes (room_id, starts_at, id) WHERE NOT is_cancelled`;
  `IX_enrollments_class_id_user_id` — `enrollments (class_id, user_id) INCLUDE (seats) WHERE
  status = 'active'`: префикс `class_id` покрывает сумму занятия, `class_id, user_id` — сумму
  пользователя, обе только по индексу. Выданные `IX_classes_room_id` и `IX_enrollments_class_id`
  остаются. Имена — по соглашению EF, как у выданных;
- объявление — `HasIndex(...).HasFilter(...)` и `IncludeProperties` в выданных
  `ClassConfiguration` и `EnrollmentConfiguration` (прецедент — `HasCheckConstraint` из 7.2),
  миграция `AddScheduleIndexes` генерируется, снимок модели знает про индексы. Не
  `migrationBuilder.Sql`: следующий `migrations add` их бы не видел;
- TDD — тест плана в `ScheduleRepositoryTests`: на клоне SQL, который EF реально генерирует для
  страницы расписания (из лога команды или `ToQueryString()`), под `SET LOCAL enable_seqscan =
  off` в `EXPLAIN (FORMAT JSON)` — занятия читаются через `IX_classes_starts_at_id`, с залом —
  через `IX_classes_room_id_starts_at_id`, суммы — через `IX_enrollments_class_id_user_id`.
  Красный до миграции. Ловит главный риск: предикат частичного индекса не совпал с тем, что
  генерирует EF (`NOT is_cancelled`, `status = 'active'`), и индекс молча не используется. Без
  `enable_seqscan = off` на маленькой базе планировщик выберет полное сканирование. Если план
  частичный индекс не берёт — полные индексы и причина сюда;
- ручная проверка: скрипт `docs/schedule-explain.sql` коммитится — отдельная база из чистой
  миграции, `generate_series`: 500 тыс. занятий в 50 залах, 10 % отменённых, 3 млн броней;
  `ANALYZE`; `EXPLAIN (ANALYZE, BUFFERS)` по SQL из лога EF — первая страница, середина
  по курсору, с залом и без. Вывод — в `NOTES.md`, «Расписание»;
- старт на чистой базе: `docker compose down -v`, команды из `README`, `/health`
  и `/health/ready` — схема меняется.
