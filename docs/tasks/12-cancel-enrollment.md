# 12. Отмена брони (§3)

Статус: проработано

Без очереди.

- повторный вызов возвращает тот же `refundedVisits` — его нужно хранить;
- сидер срабатывает только на пустой базе: в существующей базе новую колонку заполняет миграция,
  а сидер правится для новой;
- в сидах за отменённые брони посещения не списывались, и все они отменены больше чем за 2 часа
  до начала; у двух из них `cancelled_at` позже момента заполнения базы — не опираться на эту
  дату при заполнении;
- правило двух часов;
- занятие, отменённое клубом: возврат полный, отмена возможна и после начала; такое занятие
  скрыто фильтром — как в задачах 8 и 11, иначе полный возврат не применить;
- блокировки по решению задачи 4: найти бронь по id и владельцу без отслеживания, замок
  занятия, перечитать бронь, абонемент `FOR UPDATE`. Тест: две параллельные отмены одной брони
  возвращают посещения один раз;
- часы — после последнего замка (абонемента), как в задаче 8: правило двух часов сверяется
  с ними;
- события (задача 6): возврат посещений (`club.visits.refunded`) и отдельное событие отмены
  без возврата меньше чем за 2 часа; повторная отмена событий не пишет.

Разбита на подзадачи 12.1–12.4 по образцу задачи 8, каждая — свой коммит и своя строка
статуса, порядок по номерам. Наблюдаемость последней, как в 8.4: отказы уже логирует `Reject`
(задача 7), остаются события успеха.

Решено при разборе (вопросы и ответы до кода), общее для подзадач:

- колонка `refunded_visits int NULL` в `enrollments`: `NULL` у активной брони, число
  у отменённой. `CHECK ((status = 'active') = (refunded_visits IS NULL))` и
  `CHECK (refunded_visits >= 0)` — последний рубеж, как `remaining_visits >= 0` (задача 4):
  отмена без записи возврата даёт `500`, а не тихий ноль. `NOT NULL DEFAULT 0` не взяли —
  по нему не отличить «не отменена» от «отменена без возврата»;
- засеянным отменённым броням — `refunded_visits = seats`: все они отменены больше чем за 2 часа
  до начала, по §3 это полный возврат, а «списали и вернули» на остатке то же, что «не
  списывали». `0` означал бы сгоревшие посещения, и остаток в базе был бы меньше. Миграция
  (`UPDATE … WHERE status = 'cancelled'`) и сидер ставят значение без условий, не опираясь
  на `cancelled_at`; пометка `// решение:` у обоих;
- порядок: бронь по id и владельцу без отслеживания (`404`; уже `cancelled` — сразу `200`
  с сохранённым результатом, без замков и транзакции) → замок занятия
  `LockIncludingCancelledAsync` → бронь перечитывается с отслеживанием (уже отменена
  параллельной отменой — сохранённый результат) → абонемент `LockByUserAsync` **всегда**, даже
  без возврата → один `now` → занятие отменено клубом: полный возврат; `now >= startsAt`:
  `409 class-started`; `startsAt - now >= 2h`: полный возврат, иначе `0`;
- быстрый путь для отменённой брони безопасен: `cancelled` — конечный статус, а
  `refunded_visits` пишется в той же транзакции, что и статус. Повтор на горячем занятии
  не ждёт замок и не получает `503`. «Без быстрого пути» задачи 9 сюда не относится: там ключ
  мог откатиться, бронь — нет;
- абонемент блокируется всегда, а часы читаются после него (правило 8.3 «часы — после
  последнего замка»): иначе решение о возврате принималось бы до ожидания на абонементе,
  и за `lock_timeout` граница двух часов прошла бы незамеченной;
- правила сверяются по сырому `now`, `cancelled_at` — усечённый до микросекунд `now`. Усечённый
  на тик ближе двух часов дал бы ровно `startsAt − 2h` и полный возврат вопреки §3. Следствие:
  в базе бывает `cancelled_at`, равный `startsAt − 2h`, при нулевом возврате. Пометка
  `// решение:`;
- просроченный или исчерпанный абонемент возврату не мешает;
- переполнение остатка (`remaining_visits + seats > int.MaxValue`, абонемент пополнили мимо
  API) — `500`, транзакция откатывается. `checked` не пишется: сумма двух неотрицательных `int`
  при переполнении всегда отрицательна, её ловит `CHECK remaining_visits >= 0`, и тест
  с `checked` и без него одинаков — у `checked` не было бы red-фазы. Пометка `// решение:`
  у возврата — про `CHECK`. Состояние вне контракта: своя причина `409` ломает контракт,
  частичный возврат молча теряет посещения;
- админ на чужую бронь — `404`, как в задаче 11;
- отменил меньше чем за 2 часа, потом клуб отменил занятие: повторный вызов — `200` с тем же `0`,
  посещения не возвращаются (§3: «тот же результат, ничего не меняя»). Упомянуть в заметках
  к сдаче как известное следствие;
- замки (`LockIncludingCancelledAsync`, `LockByUserAsync`) уже есть и берутся сразу в 12.1;
  тесты 12.3 зелёные с первого прогона, что они ловят регрессию — проверить поломкой, как в 8.3;
- чтение до замка — новый `IEnrollmentRepository.FindOwnedAsync(id, userId)`: `AsNoTracking`,
  без `Include`, «нет» и «чужая» — одна ветка `null`. После замка бронь перечитывается выданным
  `GetByIdAsync` (отслеживает; у броней фильтра нет);
- `EnrollmentService.CancelAsync(userId, id)` → `CancelResult`: `Cancelled(Id, RefundedVisits,
  RemainingVisits?, Repeated)`, `NotFound`, `Rejected(reason)`. `Repeated` нужен 12.4: повтор
  событий не пишет. Ответ — `CancelEnrollmentResponse(id, status, refundedVisits)`, `status`
  из базы;
- хелперы тестов под `CHECK`: `TestData.EnrollmentAsync` получает `int? refundedVisits` —
  у отменённой брони по умолчанию `seats`, у активной всегда `NULL`; `AddEnrollmentAsync`
  в `EnrollmentRepositoryTests` пишет `seats` у отменённых; `TestDataTests` проверяет колонку.
  Выданные тесты (`Existing/`) вставляют только активные брони, `CHECK` им не мешает;
- тесты — в `Enrollments/`: `CancelEnrollmentTests` (12.1), `CancelEnrollmentRuleTests` (12.2),
  `CancelEnrollmentConcurrencyTests` (12.3), `CancelEnrollmentObservabilityTests` (12.4),
  `RefundedVisitsMigrationTests` (миграция и сидер), общие хелперы — `CancelApi.cs` по образцу
  `EnrollApi.cs`;
- `AssertNoCancelTraceAsync` в `CancelApi.cs`: бронь активна, `cancelled_at` и
  `refunded_visits` — `NULL`, остаток прежний; с 12.4 — ещё нет событий 2002/2003 этого
  пользователя и сумма `club.visits.refunded` равна сумме `RefundedVisits` событий 2002.
  Применяется к `409`, `404`, `400`, `503` и переполнению.

## 12.1 Контракт и отмена

Статус: проработано

- эндпоинт на `ClubApiController`, транзакция через `TransactionRunner`;
- `401`; `400`: нечисловой id, id больше `long` (решение задачи 2); `404`: брони нет, чужая
  бронь, чужая бронь для админа (`admin001`), id `0` и отрицательный; тела `404` для «нет»
  и «чужая» совпадают, кроме `traceId`;
- `200` больше чем за 2 часа до начала: тело с точными значениями, в базе бронь `cancelled`,
  `cancelled_at` равен часам, места свободны, посещения возвращены полностью;
- тело ответа — JSON целиком, как в задаче 11: ровно `id`, `status`, `refundedVisits`, без
  лишних полей;
- «места свободны» — наблюдаемо: занятие заполнено бронью целиком, после отмены запись другого
  клиента на него — `201`;
- тела у запроса нет: POST с JSON-телом — `200`, тело игнорируется (неизвестные поля
  по контракту игнорируются);
- колонка `refundedVisits`: миграция заполняет её в существующей базе, сидер — в новой
  (ловушки сидов — выше); старт на чистой базе — схема меняется;
- повторный вызов — тот же `refundedVisits`, в базе ничего не меняется;
- отмена брони, отменённой ещё в сидах: `200` и `refundedVisits`, которым её заполнили миграция
  и сидер; остаток и места не меняются.

Решено при разборе:

- минимальный код всегда возвращает посещения полностью; тесты 12.1 берут занятие дальше чем
  через 2 часа. Правило двух часов, `class-started`, отменённое клубом занятие и переполнение —
  в 12.2;
- миграция: добавить колонку → `UPDATE … SET refunded_visits = seats WHERE status = 'cancelled'`
  → `CHECK`. `CHECK` до `UPDATE` уронил бы миграцию на засеянных отменённых бронях;
- тест миграции — на клоне засеянного шаблона (`TestDb.CloneAsync`): `IMigrator.MigrateAsync`
  откатывает до `AddIntegrityConstraints` и снова накатывает — у всех засеянных отменённых
  (50 штук, проверено по базе compose: ни одна не отменена ближе двух часов до начала, минимум
  6 часов) `refunded_visits = seats`, у активных `NULL`. Так проверяются настоящие сиды,
  а не только вставленные руками строки. Что `IMigrator.MigrateAsync(targetMigration)`
  в EF Core 9 откатывает так — проверить до кода. Сидер — по шаблонной базе без отката:
  у всех отменённых `refunded_visits = seats`, у активных `NULL`. Старт на чистой базе
  (`docker compose down -v` и команды `README`) — вручную;
- в `NOTES.md` при реализации — решение о заполнении колонки у засеянных броней;
- `CHECK` — тест репозитория (`TestDb.CloneAsync`): отменённая с `NULL`, активная с числом
  и отменённая с `-1` — `23514`;
- `FindOwnedAsync` — тесты в `EnrollmentRepositoryTests`: своя бронь находится, чужая
  и несуществующая — `null`, бронь на отменённом занятии находится (ловушка фильтра), сущность
  не отслеживается.

## 12.2 Правило двух часов, `class-started` и отменённое занятие

Статус: проработано

- правило двух часов: ровно 2 часа до начала, на тик меньше и на тик больше; меньше чем
  за 2 часа — места свободны, `refundedVisits` равен 0, остаток прежний;
- `409 class-started` при `startsAt`, равном текущему моменту, и после; на тик раньше — `200`;
  отказ не оставляет следов;
- уже отменённая бронь после начала занятия — `200` с прежним результатом, не `class-started`;
- занятие, отменённое клубом: полный возврат меньше чем за 2 часа и после начала, без
  `class-started`; фильтр занятий не должен превращать такую отмену в `404`.

Решено при разборе:

- граница — переводом часов: ровно `startsAt − 2h` — полный возврат; на тик ближе — `0`
  (сравнение по сырому `now`, выше); на тик дальше — полный возврат;
- отмена при просроченном и при исчерпанном абонементе — полный возврат с точным остатком;
- переполнение: остаток `int.MaxValue`, бронь на 1 место — `500`, следов нет (ловит `CHECK`
  базы, выше); бронь на `int.MaxValue` мест при остатке `0` — `200`, остаток `int.MaxValue`;
- отменил меньше чем за 2 часа (`0`), затем занятие отменено клубом — повтор `200` с `0`,
  остаток прежний. В `NOTES.md` при реализации — как известное следствие §3.

## 12.3 Конкурентность и часы

Статус: проработано

- блокировки по решению задачи 4 (выше): бронь без отслеживания, замок занятия, бронь
  перечитывается, абонемент `FOR UPDATE`;
- две параллельные отмены одной брони: обе `200` с одним `refundedVisits`, посещения
  возвращены один раз;
- две параллельные отмены одного пользователя на разных занятиях — как гонка за посещения
  в 8.3: замки занятий их не разводят, тест держит строку абонемента; оба возврата дошли
  до остатка. Без `FOR UPDATE` абонемента один возврат теряется;
- часы после замка: тест держит замок, переводит часы за границу двух часов, отпускает —
  `refundedVisits` равен 0; за `startsAt` — `409 class-started`;
- `503` на эндпоинте: бронь не отменена, остаток прежний.

Решено при разборе:

- часы: держим занятие, часы за границу двух часов — `0`; держим абонемент, часы за границу —
  `0`, за `startsAt` — `409 class-started` (ловит чтение часов между замками);
- `503`: держим занятие — `503`, `Retry-After: 1`, `lock-timeout`, бронь активна, остаток
  прежний; держим абонемент — то же;
- быстрый путь: держим замок занятия, повторная отмена уже отменённой брони — сразу `200`
  с сохранённым результатом, без `503`;
- итоговый тест без замка теста (`[DoNotParallelize]`): десять параллельных отмен одной брони
  на 3 места — все `200` с `refundedVisits = 3`, остаток вырос ровно на 3, `cancelled_at` один;
- что тесты ловят регрессию — поломкой: чтение без замка занятия и без замка абонемента.
