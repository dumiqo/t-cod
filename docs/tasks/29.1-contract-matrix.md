# 29.1 Контрактная матрица

Статус: готово

Проверка обязательного функционала: строки таблиц кодов и причин `409` из `ЗАДАНИЕ.md` и общие
правила — против тестов. Пункты «Правила» разделов в сверку не входят.

- тесты на готовый код зеленеют сразу: красную фазу получаем, временно ломая реализацию
  (`CLAUDE.md`), в отчёте — прогон с поломкой и без; поломки не коммитятся;
- расхождение с контрактом, если найдётся, — тест-воспроизведение и исправление в этой же
  подзадаче, нюанс дописать сюда.

## Результат

Сверка проведена при проработке. Полную матрицу «каждая строка → тест» не ведём: она нужна
как метод поиска дыр, а держать её в актуальном виде дорого — имена тестов уплывают. После
реализации здесь остаётся:

- короткая таблица `§ | строка контракта | тест (29.1)` — только строки, закрытые в этой
  подзадаче. Правило, которое один `DataRow`-тест проверяет на всех восьми, — одна строка
  с § = `§1–§8`;
- фраза: «остальные строки таблиц кодов, причин `409` и общих правил покрыты тестами
  задач 8–28, сверено в 29.1».

## Дыры и тесты

### 1. `401` на всех восьми — `Contract/AuthMatrixTests`

Сейчас: §1 — без токена и чужая подпись; §3, §4, §6, §8 — без токена и мусор; §2, §5, §7 —
только без токена; истёкшего токена нет нигде.

`Request_InvalidToken_Returns401WithoutTrace(endpoint, token)` — `DataRow` 8 эндпоинтов ×
5 вариантов = 40:

- без заголовка `Authorization`;
- мусор: `Bearer not-a-token`;
- чужая подпись: наши `Issuer` / `Audience` / claims, ключ `new string('x', 64)`
  (как `EnrollTests.ForgedToken`);
- истёкший: наш ключ, `expires = DateTime.UtcNow - 1 мин`. Срок JWT сверяется с реальными
  часами, а не с `app.Clock` (задача 7, `HarnessMe_TokenExpiredByRealTime_Returns401`) —
  сдвиг фейковых часов токен не просрочит;
- `alg: none`: заголовок `{"alg":"none","typ":"JWT"}` и корректный payload (наши `iss`, `aud`,
  `nameid` тестового пользователя, `role`, `exp` в будущем) в base64url, пустая подпись
  (`header.payload.`).

Запрос во всём, кроме токена, валиден: реальный id своей брони / записи в очереди, корректное
тело, `Idempotency-Key`, правильные параметры; §6 — параметры для админа.

Проверки: `401`; `WWW-Authenticate` начинается с `Bearer`; тело пустое (`error_description`
JwtBearer не пиним); снимок «без следов» не изменился.

### 2. `401` раньше остальных кодов — `Contract/AuthMatrixTests`

Порядок `401` → `429` → `403` → `400` → `404` → `409` (`NOTES.md`, «Порядок кодов ответа»)
тестами закреплён только для `429`. `Request_NoTokenAndInvalidInput_Returns401(endpoint, …)`,
без токена плюс одно нарушение на эндпоинт:

| § | нарушение |
|---|---|
| §1 | битый JSON (`{`) и нет `Idempotency-Key` |
| §2 | нечисловой id и битый JSON |
| §3, §4, §8 | нечисловой id |
| §5 | нет `from` и `to` |
| §6 | нет `from` и `to` |
| §7 | битый JSON и нет `Idempotency-Key` |

Ожидаем `401` и снимок без изменений.

### 3. Пользователь из токена и неизвестные поля — `Contract/IdentityFromTokenTests`

У §7 неизвестные поля не проверены; правило «пользователь определяется по токену, не по телу
или строке запроса» не закреплено нигде. Существующие тесты §1, §2 не трогаем.

- §1, §2, §7: тело с лишними `userId` (id другого тестового пользователя), `id`,
  `status: "cancelled"` и вложенным объектом. Бронь / запись — у пользователя из токена,
  посещения списаны у него, у другого пользователя снимок не изменился;
- §5: `?userId=<другой>` — `mySeats` считается по пользователю из токена (у другого есть
  бронь на том же занятии с другим числом мест).

### 4. Админ на семи обычных эндпоинтах — `Contract/AdminAccessTests`

Роль важна только для §6; тестов, где админ успешно пользуется остальными, нет (есть только
«админ на чужой брони → `404`»). `Request_AdminOnOwnData_SucceedsLikeUser(endpoint, status)`:
§1 → `201`, §2 → `200`, §3 → `200`, §4 → `200`, §5 → `200` со своим `mySeats`, §7 → `201`,
§8 → `200`. Проверка тела и состояния — как у пользователя.

Админа создаёт `TestData.UserAsync(…, role: "admin")` — новый необязательный параметр
(по умолчанию `"user"`). Сидовый `admin001` не берём: случайный абонемент и общий пользователь
у параллельных тестов.

### 5. Ключ после `already-waiting` — `Waitlist/JoinWaitlistRejectionTests`

`Join_AlreadyWaitingWithOtherSeats_Returns409AlreadyWaitingEntryUnchanged` сверяет очередь
и остаток, но не ключ: `WaitlistApi.AssertNoTraceAsync` здесь неприменим — запись у пользователя
уже есть. Существующий тест не меняем, новый рядом:

- ключ A — запись создана; ключ B — `409 already-waiting`;
- строки ключа B нет; событий 3001 и прироста `club.waitlist.joined` за второй запрос нет;
- после ухода из очереди повтор с ключом B — `201` и новая запись (ключ отказом не занят).

## Хелпер снимка «без следов» — `Contract/`

Готовые `EnrollApi.AssertNoTraceAsync` / `WaitlistApi.AssertNoTraceAsync` рассчитаны
на пользователя без данных; у §2, §3, §8 бронь или запись уже есть. Новый хелпер: снимок до
и после запроса строк `enrollments`, `waitlist_entries`, `passes`, `idempotency_keys` тестового
пользователя и занятия (через `app.CreateContext()`), плюс ни одного события успеха 2001–2005,
3001–3004 и отказа 1001, метрики успеха (`club.enrollments.created`, `club.visits.charged`,
`club.visits.refunded`, `club.idempotency.replayed`, `club.waitlist.*`) не выросли.
Существующие хелперы не меняем.

## Красная фаза

Одна временная поломка на группу:

| группа | поломка |
|---|---|
| `401` | убрать `[Authorize]` с `ClubApiController` |
| `alg: none` | `RequireSignedTokens = false` и `SignatureValidator`, возвращающий токен без проверки |
| `401` раньше остальных | убрать `[Authorize]` у одного действия (свой прогон на каждое не нужен — достаточно увидеть красный `DataRow`) |
| неизвестные поля | `JsonUnmappedMemberHandling.Disallow` в настройках JSON |
| пользователь из токена | брать id пользователя из тела вместо `CurrentUserId` |
| админ | `[Authorize(Roles = "user")]` на `ClubApiController` |
| ключ после `already-waiting` | занимать ключ до проверки причин |

## За рамками

Токен с валидной подписью для несуществующего пользователя не проверяем: токены выдаёт только
`/auth/login` существующим пользователям, пользователи не удаляются, клиента без абонемента
не бывает. Поведение (вероятно `500` — абонемента нет) не проверялось. Строка в `NOTES.md`,
раздел «За рамками».
