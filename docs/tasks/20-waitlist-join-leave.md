# 20. Встать в очередь и уйти (§7, §8)

Таблица очереди, позиция, причины отказа, идемпотентность для §7. Отменённое занятие скрыто
фильтром — как в задаче 8: без `IgnoreQueryFilters()` вместо `409 class-cancelled` будет `404`.

Порядок причин — по задаче 3: тест на каждую пару причин (6 пар).

§7 и §8 — под замком занятия (решение задачи 4). Без него постановка может увидеть «мест
не хватает», пока параллельная отмена освобождает места и продвигает очередь без неё, и запись
будет ждать при свободных местах. Ключ идемпотентности §7 — после замка занятия, как в задаче 10.

Порядок очереди: `createdAt`, взятый до ожидания замка, расходится с порядком коммитов. A пришёл
раньше, B первым получил замок и ответ `position: 1`; затем A коммитится с меньшим `createdAt`,
тоже получает `position: 1` и встаёт перед B. Варианты: сортировать по `id` — он выдаётся при
вставке под замком занятия; брать время после замка — это правило уже
действует для всех пишущих запросов (задача 8).

События (задача 6): постановка и уход — `club.waitlist.joined` и `club.waitlist.left`, после
коммита; отказы §7 — `operation = join-waitlist`; повторный уход событий не пишет.

Разбита на подзадачи 20.1–20.6, каждая — свой коммит и своя строка статуса, порядок по номерам.
Схема таблицы и порядок очереди — по решениям задач 18 и 19, идемпотентность — механизм
задачи 10. Вопрос о свободных местах при непустой очереди решён заранее и записан в задаче 21:
места общие, `seats-available` — `capacity − SumActiveSeatsAsync(classId) ≥ seats`, §1 не меняется.

Перед реализацией задача прорабатывается заново: текст ниже — знания на момент первого разбора,
статуса «проработано» нет. Реализуется после готовой задачи 10 (20.4 подключает её механизм);
до 20.4 заголовок `Idempotency-Key` в §7 обязателен, но не сохраняется.

Согласовано при первом разборе:

- код: отдельный `WaitlistController` с `[Route("enrollments/waitlist")]`, `WaitlistService`
  в `WebApi/Waitlist/`, свои `JoinWaitlistRequest`, `JoinWaitlistResponse`,
  `LeaveWaitlistResponse` и результаты-объединения по образцу `EnrollResult` (`EnrollRequest`
  не переиспользуется); сущность `WaitlistEntry`, константы `WaitlistStatuses` (`waiting`,
  `cancelled`, `promoted`), репозиторий `IUnitOfWork.Waitlist`; в `Operations` —
  `JoinWaitlist`, `LeaveWaitlist`, в `RejectReasons` — `SeatsAvailable`, `AlreadyWaiting`,
  `AlreadyPromoted`. Тесты — `WebApi.Tests/Waitlist/`, помощник `WaitlistApi` по умолчанию шлёт
  новый ключ, как `EnrollApi` после 10.1;
- модель — зеркально `EnrollmentConfiguration`: навигация `Class` (для `IgnoreQueryFilters()`
  в §8) с `WithMany()` без коллекции в выданном `Class`, FK на `User` без навигации, удаление
  по умолчанию;
- `400` и `404` §7 — по образцу §1 (задача 8): `classId` `0`, отрицательный или несуществующий —
  `404`; нет, `null` или не число в `classId` / `seats`, `seats ≤ 0`, переполнение `int`, тело
  не JSON, нет заголовка — `400`;
- §8: быстрый путь для конечных статусов — запись без отслеживания `cancelled` → сразу `200`,
  `promoted` → сразу `409 already-promoted`, без транзакции и замка; через замок
  и перечитывание идёт только `waiting`;
- метрики `club.waitlist.joined`, `left` (и `promoted` в задаче 23) считают места, как
  `club.enrollments.created`: «ждут мест» = joined − left − promoted. События: 3001
  `WaitlistJoined` (`waitlistId`, `classId`, `seats`, `userId`, `position`), 3002 `WaitlistLeft`
  (`waitlistId`, `classId`, `seats`, `userId`); 3003 — продвижение, задача 23.

## 20.1 Таблица очереди и постановка (§7)

- миграция таблицы очереди (id по решению задачи 18, уникальность по решению задачи 19); сиды
  не меняются; старт на чистой базе — схема меняется;
- id записи в очереди — из последовательности `enrollments.id` (задача 18): id из ответа §7
  не совпадает ни с одной бронью, следующая запись (§1) получает id больше него;
- эндпоинт, транзакция, замок занятия — первое чтение;
- `400` по таблице контракта, в том числе нет заголовка `Idempotency-Key`; `401`; `404`
  занятия нет; отменённое занятие даёт не `404`;
- `201`: тело с точными значениями, `createdAt` усечён до микросекунд; `position` считается
  среди ожидающих; в базе — запись очереди, места и остаток прежние;
- порядок очереди — по решению задачи 19 (варианты — выше);
- тесты репозитория (`TestDb.CloneAsync()`) на новые методы: своя запись по id без
  отслеживания (нет и чужая — `null`), есть ли своя `waiting` на занятии, подсчёт `position`;
- частичный уникальный индекс есть: вторая `waiting` того же клиента на то же занятие — `23505`,
  записи `cancelled` и `promoted` вставке не мешают.

По решению задачи 19:

- таблица `waitlist_entries`: `id` (default `nextval('enrollments_id_seq'::regclass)`),
  `class_id` и `user_id` с FK, `seats` (`CHECK seats >= 1`), `status` (`CHECK` по `waiting`,
  `cancelled`, `promoted`), `created_at`, `cancelled_at` (nullable); частичные индексы
  `(class_id, id)` и уникальный `(class_id, user_id)`, оба `WHERE status = 'waiting'`;
- тест на имя последовательности и на её `cache_size = 1`: монотонность id между сессиями,
  на которой держится порядок;
- `position` — число записей `waiting` того же занятия с `id ≤` своего: тест — три постановки
  дают позиции 1, 2, 3; запись `cancelled` или `promoted` впереди позицию не занимает; записи
  другого занятия не считаются;
- `created_at` — время после замка, усечено до микросекунд; порядок — по `id`, пометка
  `// решение:`.

## 20.2 Причины 409 §7 и границы

- четыре причины, на каждую — тест, что отказ не оставляет следов (очередь, места, остаток);
- 6 пар причин по приоритету из задачи 3;
- границы `seats-available`: свободно ровно запрошенное число мест и на одно меньше; отменённые
  брони мест не занимают; `startsAt` равен текущему моменту и на тик позже;
- переполненное занятие (задача 1: свободных мест меньше нуля) — постановка проходит;
- `already-waiting`, повторная постановка после ухода и после продвижения, запрос больше
  вместимости, проверка абонемента — по решению задачи 19:
  - `already-waiting` — только при своей записи `waiting` на это занятие; отказ не оставляет
    следов; своя запись `waiting` на другом занятии и чужая на этом не мешают;
  - повторная постановка после ухода — `201`, новый id больше старого, `position` в конце
    очереди; после продвижения (запись `promoted`, есть активная бронь) — тоже `201`;
  - абонемент не проверяется (пометка `// решение:`): просроченный (`validUntil` вчера)
    и с нулём посещений — `201`, остаток посещений прежний;
  - запрос больше вместимости (`seats = capacity + 1`) — `201`, запись в базе (пометка
    `// решение:`).

## 20.3 Уход из очереди (§8)

- эндпоинт под замком занятия: запись очереди читается по id и владельцу без отслеживания,
  замок занятия, запись перечитывается — как бронь в задаче 12; `cancelled` и `promoted` —
  быстрый путь без замка (выше), после замка статус проверяется снова: параллельный уход —
  `200` без события;
- `401`; `400`: нечисловой id, id больше `long` (решение задачи 2); `404`: записи нет, чужая
  запись (и для админа, как в задаче 11), id `0` и отрицательный;
- запись на отменённом занятии: обращение к `e.Class` с фильтром даёт `404` — как в задачах 11
  и 12; уход с отменённого и с начавшегося занятия — по решению задачи 19: оба `200`, запись
  `cancelled`; граница — `startsAt` равен текущему моменту;
- `200` с точным телом; в базе запись `cancelled`, `cancelled_at` — момент ухода. `position` в контракте видна только
  в ответе §7, поэтому «стоявшие за ней поднялись» проверяется так: следующий вставший получает
  позицию на единицу меньше, порядок ожидающих в базе прежний;
- повторный вызов — тот же результат, в базе ничего не меняется;
- уход, когда запись уже стала бронью, — по решению задачи 19: `409` с `reason:
  already-promoted` (пометка `// решение:`), запись `promoted` и бронь в базе не изменились;
  так же, если бронь потом отменили. Продвижения ещё нет (задача 23) — тест готовит запись
  `promoted` и бронь с тем же id прямо в базе.

## 20.4 Идемпотентность §7

- миграция `idempotency_keys`: колонка `result_position` (nullable, как остальной снимок),
  значение `JoinWaitlist` ↔ `join-waitlist` в `IdempotentOperation` и в `CHECK` по `operation`
  (задача 10 завела их только для `enroll`); юнит-тест сопоставления покрывает новое значение;
- ключ после замка занятия, как в задаче 10; повтор раньше любой причины `409`: повтор
  не получает `already-waiting`;
- на повтор `position` — снимок из первого ответа (решение задачи 9): тест — после постановки
  впереди стоящий уходит, повтор отдаёт прежнюю `position`; так же после продвижения записи;
- повтор со старым ключом после ухода (§8) — снимок `201` со старыми `id` и `position`,
  в очередь не ставит: в базе одна запись `cancelled`; новая постановка — с новым ключом;
- тот же ключ, что у записи §1, — не повтор: область ключа — пользователь и операция;
- два одновременных запроса с одним ключом — одна запись в очереди.

## 20.5 Конкурентность и часы

- порядок очереди при замке: тест держит замок занятия, A и B встают в ожидание, ответы
  `position` и порядок в базе совпадают с порядком коммитов;
- две одновременные постановки одного клиента — одна запись, второй `already-waiting`;
- часы после замка: тест держит замок, переводит часы за `startsAt` — `409 class-started`;
- `503` на §7 и §8: записи в очереди не изменились;
- быстрый путь §8: тест держит замок занятия, повторный уход и уход по записи `promoted`
  отвечают сразу (`200` и `409 already-promoted`), без `503`.
