# 19. Исследование: прочее по очереди

Статус: проработано

- проверять ли абонемент при постановке: в причинах §7 нет `pass-*`;
- запрос на больше мест, чем вместимость занятия: такая запись будет ждать вечно;
- уход из очереди (§8), когда запись уже стала бронью: в ответе §8 разрешён только статус
  `cancelled`;
- уход из очереди на отменённом клубом или уже начавшемся занятии: в таблице §8 нет `409`,
  своя причина возможна (раздел «О листе ожидания в целом»);
- повторная постановка после ухода из очереди или после продвижения в бронь: от этого зависят
  `already-waiting` и уникальный индекс;
- порядок очереди: по `id` или по времени, взятому после замка (варианты — в задаче 20). Решить
  здесь, а не в 20.1: от этого зависят индекс таблицы и подсчёт `position`.

## Проработка

Согласованные решения; при выполнении задачи они записываются в заметки, раздел «Прочее
по очереди».

Факты:

- `enrollments.status` — текст без `CHECK` в выданной схеме, у брони есть `cancelled_at`;
- повтор §8 обязан отдать `200` и тот же результат — запись после ухода из базы не удаляется;
- по задаче 18 продвинутая запись выходит из очереди, а её id становится id брони;
- по задаче 9 повтор §7 с тем же ключом и телом отдаёт снимок первого ответа раньше любой
  причины `409`.

Решения:

- **Хранение.** Строка очереди остаётся навсегда, состояние — в `status`: `waiting`,
  `cancelled` (ушёл через §8), `promoted` (стал бронью). Таблица `waitlist_entries`: `id`
  (default из `enrollments_id_seq`, задача 18), `class_id` и `user_id` с FK, `seats`
  (`CHECK seats >= 1`), `status` (`CHECK` по трём значениям), `created_at`, `cancelled_at`
  (nullable, для диагностики, в ответы не попадает). Время продвижения отдельно не хранится:
  это `enrollments.created_at` брони с тем же id. Не взяли: удаление строки — повтор §8 дал бы
  `404`; отдельную таблицу истории — сложнее без пользы.
- **Абонемент при постановке не проверяется** (пометка `// решение:`). Посещения списываются
  при продвижении — §3: «ожидание превращается в обычную активную бронь»; что делать
  с ожидающим без посещений или с истёкшим абонементом, решает задача 21. Пока клиент ждёт,
  он может вернуть посещения отменой другой брони. Свои причины `pass-*` в §7 не взяли:
  контракт их не перечисляет, проверка вправе ждать `201`.
- **Запрос больше вместимости принимается** (`201`, пометка `// решение:`): правило §7
  «свободных мест меньше, чем запрошено» выполнено, вместимость может вырасти мимо API; особого
  случая нет, как в §1 («одно правило проще двух», раздел «Приоритет причин 409»). Ограничение
  для задачи 21: запись, которая не помещается даже в пустое занятие, не держит очередь. Если 21
  выберет строгий порядок «ждём, пока хватит первому», этот вопрос открывается заново.
- **Уход с отменённого клубом или начавшегося занятия разрешён**: `200`, запись → `cancelled`.
  Уход не трогает ни места, ни посещения, продвижения на таком занятии нет, отказывать не в чем,
  а клиенту нужен способ убрать мёртвую запись. Занятие читается с `IgnoreQueryFilters()`,
  иначе `404`.
- **Уход, когда запись уже стала бронью** — `409` со своей причиной `already-promoted`
  (пометка `// решение:`, строка в заметках, отказ с `operation = leave-waitlist`). Причина
  подсказывает выход: места уже за клиентом, снимать — бронь §3 с тем же id. Так же, если
  бронь потом отменили: из очереди запись ушла продвижением, не через §8. Других `409` у §8 нет,
  шкала приоритета не нужна. Не взяли: `200 cancelled` без отмены брони — ложный ответ;
  `200` с отменой брони — скрытая отмена с правилом двух часов через чужой эндпоинт; `404` —
  противоречит повтору §8 после своего ухода и прячет причину.
- **Повторная постановка.** `already-waiting` — только при записи этого клиента на это занятие
  в статусе `waiting`. После ухода и после продвижения встать снова можно: новая запись, новый
  id, конец очереди (§7: «активные брони не мешают»). Защита в базе — частичный уникальный
  индекс `(class_id, user_id) WHERE status = 'waiting'`; под замком занятия до него не доходит,
  нарушение — `500`, как `passes.user_id`. Следствие задачи 9: повтор §7 со старым ключом после
  ухода отдаёт снимок `201` со старыми `id` и `position` и в очередь не ставит — для новой
  постановки нужен новый ключ.
- **Порядок очереди — по `id`** (пометка `// решение:`). `position` — число записей `waiting`
  того же занятия с `id ≤` своего, считается в транзакции постановки после вставки. `nextval`
  выполняется при `INSERT` (EF вставляет без id и читает его `RETURNING`), то есть под замком
  занятия, — на одном занятии порядок id совпадает с порядком коммитов; при `CACHE 1`
  у последовательности (сейчас так) значения монотонны между сессиями. `created_at` берётся
  после замка, как у всех пишущих запросов, — «порядок по времени постановки» из контракта
  соблюдён. Не взяли сортировку по `created_at`: в тестах часы стоят и время совпадает, в жизни
  оно может пойти назад, разбор равных всё равно потребовал бы `id`. Индекс — частичный
  `(class_id, id) WHERE status = 'waiting'`.

Тесты — в подзадачах 20.1–20.6 и 23.1 (дописаны в их тексты); ограничение для очереди
продвижения — в тексте задачи 21.
