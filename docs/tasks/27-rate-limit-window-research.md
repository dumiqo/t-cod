# 27. Исследование: окно ограничения частоты

- скользящее или фиксированное окно; фиксированное по минутам часов пропустит 61-й запрос,
  если серия пересечёт границу минуты;
- где хранить счётчик: приложение может работать в нескольких экземплярах, Redis есть;
- считаются ли отклонённые `429`;
- лимит только на восемь эндпоинтов задания: вход и `/health` не трогать;
- окно считается по `TimeProvider`, а не только по TTL в Redis: тест переходит границу окна
  переводом часов, без ожидания (решение задачи 5).

Найдено при разборе:

- маршрутизация в `Program.cs` неявная и стоит в начале конвейера: middleware между
  `UseAuthentication` и `UseAuthorization` уже видит эндпоинт и его метаданные;
- score в sorted set — double: тики `DateTimeOffset` (~6·10¹⁷) в 53 бита мантиссы точно
  не помещаются, Unix-миллисекунды (~1,8·10¹²) — помещаются;
- встроенный ограничитель держит состояние в памяти процесса; для Redis нужен свой подкласс
  `RateLimiter`, а не настройка;
- TTL ключа в Redis идёт по реальным часам, а фейковые стоят: правильность окна не может
  держаться на TTL, только на моментах из `TimeProvider`.

Решение — в заметках, раздел «Окно ограничения частоты»: скользящий журнал в sorted set Redis
`rate:{userId}`, интервал `(t − 60 с, t]` в миллисекундах `TimeProvider`, один Lua-скрипт
на запрос, `429` в журнал не попадают и получают `Retry-After`. Свой middleware между
аутентификацией и авторизацией по метке на `ClubApiController`, без встроенного `AddRateLimiter`;
60 и минута — константы. Реализация — в 28.1, отказ Redis — в 28.2.
