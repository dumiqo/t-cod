# 29.3 Инварианты под смешанной нагрузкой

Тест в `dotnet test` (`[DoNotParallelize]`): все пишущие эндпоинты одновременно на одних
и тех же занятиях, затем проверка инвариантов базы. Ответ на «несколько человек на последнее
место — без перезаписи» сразу для всех путей изменения мест.

- уже есть гонки по одному виду (запись на последнее место, увеличение мест против записи,
  отмена с продвижением против записи, пачка в `PromotionConcurrencyTests`); здесь — смесь:
  десятки пользователей, несколько занятий на 1–3 места, параллельно §1, §2, §3, §7, §8
  и повторы §1 / §7 с тем же `Idempotency-Key`;
- инварианты после прогона, через свой `DbContext`:
  - сумма мест активных броней каждого занятия не больше `seats`;
  - по каждому абонементу: начальный остаток = текущий + списано по активным броням
    (с учётом возвратов по правилу двух часов);
  - нет двух активных записей пользователя в очереди одного занятия, позиции без дыр
    и повторов;
  - каждый `201` / `200` клиента есть в базе, каждый отказ — нет;
  - ни одного `500`; `503` допустимы только с `Retry-After`;
  - события и метрики успеха совпадают с числом успешных ответов;
- один и тот же сценарий в трёх режимах Redis: работает, сломан (`BreakRedis`), завис
  (`FreezableRedisProxy`) — DataRow;
- лимит 60 в минуту не должен мешать: запросов на пользователя меньше 60 или часы двигаются
  между волнами;
- недетерминированный порядок — не повод для нестабильного теста: проверяются только
  инварианты, не конкретный победитель. Нужен фиксированный seed генератора сценария,
  чтобы упавший прогон можно было повторить;
- красная фаза — временно убрать блокировку занятия (или проверку вместимости) и увидеть,
  что инвариант ловит перезапись.
