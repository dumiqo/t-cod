# 29.3 Инварианты под смешанной нагрузкой

Статус: проработано

Тест в `dotnet test` (`[DoNotParallelize]`): все пишущие эндпоинты одновременно на одних
и тех же занятиях, затем проверка инвариантов базы. Ответ на «несколько человек на последнее
место — без перезаписи» сразу для всех путей изменения мест.

- уже есть гонки по одному виду (запись на последнее место, увеличение мест против записи,
  отмена с продвижением против записи, пачка в `PromotionConcurrencyTests`); здесь — смесь:
  десятки пользователей, несколько занятий на 1–3 места, параллельно §1, §2, §3, §7, §8
  и повторы §1 / §7 с тем же `Idempotency-Key`;
- инварианты после прогона, через свой `DbContext`:
  - сумма мест активных броней каждого занятия не больше `seats`;
  - по каждому абонементу: начальный остаток = текущий + списано по активным броням
    (с учётом возвратов по правилу двух часов);
  - нет двух активных записей пользователя в очереди одного занятия, позиции без дыр
    и повторов;
  - каждый `201` / `200` клиента есть в базе, каждый отказ — нет;
  - ни одного `500`; `503` допустимы только с `Retry-After`;
  - события и метрики успеха совпадают с числом успешных ответов;
- один и тот же сценарий в трёх режимах Redis: работает, сломан (`BreakRedis`), завис
  (`FreezableRedisProxy`) — DataRow;
- лимит 60 в минуту не должен мешать: запросов на пользователя меньше 60 или часы двигаются
  между волнами;
- недетерминированный порядок — не повод для нестабильного теста: проверяются только
  инварианты, не конкретный победитель. Нужен фиксированный seed генератора сценария,
  чтобы упавший прогон можно было повторить;
- красная фаза — временно убрать блокировку занятия (или проверку вместимости) и увидеть,
  что инвариант ловит перезапись.

## Сценарий

- состав смеси: §1, §2 (увеличение и уменьшение), §3, §7, §8, повторы §1 / §7 с тем же ключом.
  Чтений в смеси нет; после прогона `GET /enrollments/{id}` по каждой брони сверяется с базой —
  ловит устаревший кэш карточки после гонок во всех трёх режимах Redis;
- 40 пользователей, 4 занятия вместимостью 1 / 2 / 3 / 3. До прогона через `app.Data`
  создаются брони и записи в очереди: занятия полные и с очередью с самого начала;
- одно из четырёх занятий начинается через 1 ч (меньше двух часов): в смеси есть отмена без
  возврата и позднее продвижение. Часы стоят;
- абонементы: около четверти пользователей с остатком 1–2, двое с истёкшим — в смеси есть
  `pass-exhausted` / `pass-expired` и пропуски при продвижении;
- около 200 запросов, на пользователя не больше 10 — лимит 60 не мешает, часы не двигаются;
- две волны, внутри волны запросы стартуют разом через `Task.WhenAll`, без `HeldLock`:
  1. залп по заранее созданным броням и записям плюс новые §1 / §7;
  2. залп по id из ответов первой волны: §2 / §3 / §8 на новых бронях и записях, повторы
     ключей первой волны;
- генератор — `Random(seed)`, seed в `DataRow`; при падении в сообщении seed и дамп сценария;
- три режима Redis — `DataRow`: работает, сломан (`BreakRedis`), завис (`FreezableRedisProxy`,
  `Redis:OperationTimeout = 200 ms`). Ломается после логина клиентов, до первой волны;
- `503` не повторяются: проверяется `Retry-After` и отсутствие следов.

## Инварианты

Через свой `DbContext`, по занятиям сценария:

- сумма `seats` активных броней каждого занятия не больше вместимости;
- по каждому абонементу: `начальный = текущий + Σ seats активных броней + Σ (seats −
  refunded_visits) отменённых`. Изменения §2 в формуле не видны: они сдвигают `seats`
  и остаток на одну и ту же разницу. Остаток ни у кого не меньше 0;
- у пользователя на занятии не больше одной записи `waiting`; позиции (`waiting` по `id`)
  без дыр и повторов.

Сверка с ответами клиентов:

- каждый `201` §1 / §7 — строка с этим id, нужными владельцем и занятием. `seats` по ответам
  не сверяется: итог зависит от порядка §2, его покрывают места, остаток и карточка;
- ключи идемпотентности в базе — ровно ключи ответов `201`: у отказанных ключа нет. Повтор
  с тем же ключом вернул тот же id, что и первый;
- `200` §3 / §8 — в базе `cancelled`;
- ни одного `500`; `503` только с `Retry-After`.

Метрики и события (те же счётчики по событиям в `app.Logs`):

- `club.enrollments.created` = брони, созданные через §1;
- `club.idempotency.replayed` = повторы, вернувшие `201`;
- `club.waitlist.joined` = новые записи в очереди, `left` = `cancelled` в очереди,
  `promoted` = `promoted`;
- `club.visits.charged − club.visits.refunded` = суммарное падение остатка;
- `club.requests.rejected` = число ответов `409` и `503`.

Защита от пустого прогона: в каждом прогоне хотя бы один успех каждого эндпоинта, один
`capacity-exceeded`, одно продвижение, один повтор ключа, один `already-waiting`. Минимум
не набран — `Assert.Fail` с seed.

## Как устроены тесты

- `WebApi.Tests/Invariants/MixedLoadInvariantTests.cs` — тест (`[DoNotParallelize]`, `DataRow`
  seed × режим Redis), сверка с ответами, метриками и событиями;
- `Invariants/MixedScenario.cs` — генератор сценария по seed;
- `Invariants/InvariantChecker.cs` — независим от `TestApp`, его берёт 29.4: принимает строку
  подключения, id занятий и снимок начальных остатков, сам открывает `ClubDbContext`,
  возвращает список нарушений.

## Красная фаза

Временные поломки, не коммитятся; каждая краснеет при фиксированном seed. Если не краснеет
стабильно — усиливать нагрузку на это занятие, а не ослаблять проверку.

| поломка | что ловит |
|---|---|
| убрать блокировку занятия в §1 | сумма мест больше вместимости |
| убрать блокировку абонементов при продвижении | остаток / двойное списание |
| убрать проверку `already-waiting` | две записи `waiting` |

## Результат

`WebApi.Tests/Invariants/MixedLoadInvariantTests.cs` — один тест, 6 запусков `DataRow`
(seed 2903 и 1729 × Redis работает / сломан / завис), ~45 с на все шесть. Сценарий —
`Invariants/MixedScenario`, проверка базы — `Invariants/InvariantChecker`. На готовом коде
нарушений нет: проверки инвариантов, сверки с ответами, метрик и событий зелёные с первого
прогона; падения были только у защиты от пустого прогона (см. нюансы). Полный `dotnet test` —
1276 зелёных, два прогона подряд.

Что проверяет каждый запуск (нарушения собираются списком, `Assert.Fail` с seed и дампом
запросов):

- `InvariantChecker`: сумма мест активных броней ≤ вместимости; `остаток + Σ seats активных +
  Σ (seats − refunded_visits) отменённых` по каждому пользователю равен снимку до прогона;
  остаток ≥ 0; не больше одной `waiting` записи пользователя на занятии;
- статусы только `200 / 201 / 409 / 503`, `503` — с `Retry-After`; повтор ключа — тот же id;
- каждый `201` — строка с этим id, владельцем и занятием; множество броней в базе = заготовки
  ∪ `201` §1 ∪ продвинутые, записей очереди = заготовки ∪ `201` §7; ключи идемпотентности в базе
  ровно ключи `201` (пользователь, операция, хеш, `result_id`); `200` §3 / §8 — `cancelled`;
- метрики и события: `created` / 2001, `replayed` / 1004, `joined` / 3001, `left` / 3002,
  `promoted` / 3003 по базе и ответам, `charged − refunded` = падение остатка,
  `rejected` = `409 + 503`, 1001 = `409`, 1002 = `503`;
- карточка `GET /enrollments/{id}` каждой брони занятий сценария: `status`, `seats`,
  `pass.remainingVisits` как в базе;
- покрытие: новая бронь, новая запись в очередь, повтор ключа, `200` §2 / §3 / §8,
  `capacity-exceeded`, `already-waiting`, продвижение.

Красная фаза (временные правки, не закоммичены):

| поломка | итог |
|---|---|
| §1 без замка занятия (`GetByIdAsync` вместо `LockIncludingCancelledAsync`) | каждый прогон красный, 2–4 строки из 6: `class …: 6 active seats > capacity 3` |
| §3 читает абонементы без `FOR UPDATE` | каждый прогон красный, 2–3 строки: `user …: remaining + charged = 12, initial 10` |
| без проверки `already-waiting` | 6 из 6: `500` (уникальный индекс `waiting` в базе) |

Нюансы:

- какие именно строки краснеют, зависит от гонки; стабилен только итог «прогон красный».
  Гонке нужна точка встречи: без неё поломки 1 и 2 проходили зелёными — отсюда устройство
  сценария ниже;
- очередь забирает каждое освободившееся место: со случайной очередью на всех занятиях новых
  броней через §1 часто не было вовсе. У открытого занятия (индекс 3) в очереди только два
  истёкших абонемента — продвижение их пропускает, места достаются §1; половина новых §1 идёт
  туда же, на нём ловится перезапись мест; в первой волне §7 на него не шлются;
- первый в очереди остальных трёх занятий — один и тот же пользователь с годным абонементом,
  на 1 место, без своих броней и запросов в первой волне: отмены первой волны продвигают его на
  нескольких занятиях одновременно — гонка за один абонемент, на ней ловится поломка 2;
- в первой волне все заготовленные брони отменяются, кроме первой брони короткого занятия: она
  уменьшается или остаётся (уменьшение не отклоняется) — `200` §2 в каждом прогоне; на коротком
  занятии отмены без возврата;
- повторы ключей — только во второй волне; повтор ключа, который в первой волне получил `409`,
  создаёт запись — поэтому «созданные» считаются по различным id `201`, а не по первой волне;
- позиции в очереди не хранятся: `GetPositionAsync` считает `waiting` с `id ≤` своего, дыр и
  повторов быть не может — отдельной проверки нет;
- `InvariantChecker` для 29.4: `BalancesAsync(строка, занятия, пользователи)` до прогона,
  `CheckAsync(строка, занятия, снимок)` после; снимок учитывает заготовленные брони, поэтому
  заготовки можно создавать без списания;
- в полном прогоне режим «сломан» получил `500` `53300 too many clients already`: пул приложения
  по умолчанию 100 = `max_connections`, а чужие пулы ещё открыты. Тест задаёт
  `Maximum Pool Size=40` через `ConfigureAppConfiguration` (проверено: 41 соединение с клоном
  после волн = 40 + проверочное); в 29.4 на реальном процессе тот же предел — тема 29.5.
