# 28. Ограничение частоты

С поведением при отказе Redis по итогам задачи 24.

- место в конвейере по решению задачи 2: между `UseAuthentication` и `UseAuthorization`, ключ —
  id пользователя из токена; запросы без пользователя не считать, им ответит `401`;
- у встроенного `RateLimiterOptions` код отказа по умолчанию `503` (проверено), нужен `429`;
- лимит в тестах тот же, 60: счётчики тестов разведены префиксом ключей (решение задачи 5).
  Тесты на 61-й запрос и на новое окно — переводом фейковых часов;
- `429` — событие и `club.requests.rejected` по схеме задачи 6. Если взят встроенный
  ограничитель, у него свои метрики `aspnetcore.rate_limiting.*` — решить, нужен ли свой счётчик;
- вне лимита — `/health`, `/health/ready`, `/auth/login` и Swagger; тест на это (перенесено
  из задачи 7.4).

Разбита на подзадачи 28.1–28.2, каждая — свой коммит и своя строка статуса, порядок по номерам.
28.1 зависит только от задачи 27, 28.2 — от задачи 24 и от 26.2, если там сделана общая обёртка
над Redis.

## 28.1 Ограничитель

- окно и хранение счётчика по решению задачи 27; место в конвейере, ключ, `429` — выше;
- 60-й запрос проходит, 61-й — `429` по контракту; после перевода часов на новое окно —
  снова проходит; счётчики разных пользователей не смешиваются;
- запросы без пользователя не считаются; эндпоинты вне лимита — тест;
- считаются ли `400`, `403` и `404` — по решению задачи 2, тест на каждый;
- атомарность счётчика: 70 одновременных запросов одного пользователя — ровно 60 не-`429`;
- `429` — событие и `club.requests.rejected`.

## 28.2 Ограничение при отказе Redis

- поведение по решению задачи 24: пропускать запросы или отказывать; тест с недоступным Redis;
- события и счётчики отказа Redis — по схеме задачи 6, как в 26.2.
