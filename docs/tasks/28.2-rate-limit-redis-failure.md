# 28.2 Ограничение при отказе Redis

Статус: проработано

Поведение пересмотрено: первая версия (bf995db) при отказе Redis пропускала запрос, и лимита
не было, пока Redis лежит. Теперь решает журнал в памяти экземпляра (заметки, разделы «Отказ
Redis» и «Окно ограничения частоты»). Вызов Redis — как раньше, через «страж» из 26.4.

## Решения

- **Локальный журнал** — скользящий, с тем же окном и лимитом, что в Redis: `(t − 60 с, t]`,
  60, моменты — Unix-миллисекунды из `TimeProvider`. Ведётся всегда, а не с момента отказа:
  журнал, начатый при отказе, пустой, и на стыке пользователь получил бы до 120 запросов
  за минуту. Класс `LocalRateJournal` в `WebApi/RateLimiting/`, singleton; у каждого `TestApp`
  свой хост, тесты журнал не делят.
- **Порядок на запрос:**
  1. бронь в локальном журнале, атомарно под замком журнала: обрезать старше окна; меньше
     60 — добавить момент, иначе `429` с `Retry-After` от самого старого локального момента,
     Redis не вызывается;
  2. скрипт Redis, как в 28.1;
  3. Redis ответил `429` — бронь снимается (отказ не оставляет следов), `Retry-After` от Redis;
     принял — бронь остаётся; отказал — бронь остаётся, решение за локальным журналом, событие
     1005 `rate-limit`.
- **Локальный `429` всегда законен:** в журнале только запросы пользователя, принятые этим
  экземпляром, их не больше, чем всех принятых. Поэтому проверка при живом Redis лишнего
  не отклоняет, а после восстановления закрывает обратный стык: принятых во время отказа Redis
  не знает, а журнал помнит. На одном экземпляре лимит точный при обоих переходах.
- **Несколько экземпляров:** во время отказа лимит до 60×N; после восстановления Redis не знает
  запросов, принятых при отказе другими экземплярами (заметки, «За рамками»).
- **`429` из журнала** — тот же ответ, событие 1003 и `club.requests.rejected` с теми же тегами:
  для клиента и контракта это тот же отказ, а отказ Redis и так виден по 1005
  и `club.redis.failures`.
- **Память:** не больше 60 моментов на пользователя. Обход всех пользователей с обрезкой —
  не чаще раза в окно, по `TimeProvider`, на очередном запросе; пользователь с пустым после
  обрезки журналом удаляется. Удаление не должно терять бронь, сделанную в это же время.
- «Зависший» Redis добавляет до `Redis:OperationTimeout`, как раньше: бронь делается до вызова,
  автомата нет (задача 24). Карточка по-прежнему ждёт оба предела — лимитера и `cache-get`.
- Лимитер не повторяет ожидающие надгробия `CardCache`: общий у них только «страж».

## Тесты

Пишутся до кода. Существующие тесты 28.2 меняются: проверяемое ими поведение пересмотрено
по решению пользователя.

Меняются:

- `RateLimit_RedisBroken_RequestsOverLimitPassAndFailuresAreLogged` — при отказе 60 проходят,
  61-й — `429` с `Retry-After: 60`, событие 1003 и `club.requests.rejected`; 1005
  и `club.redis.failures` `rate-limit` — ровно 60: на 61-м Redis не вызывается;
- `RateLimit_RedisRestored_RequestsDuringOutageAreNotJournaled` — при отказе 60 проходят,
  `app.RestoreRedis()`, 61-й — `429` из журнала, ключа `rate:{userId}` в Redis нет;
  в `T + 60,000 с` — проходит.

Остаётся: `RateLimit_RedisHung_RequestPassesWithinOperationTimeout`.

Новые:

- стык при отказе: 30 при живом Redis, `app.BreakRedis()`, 30 проходят, 31-й — `429`
  с `Retry-After` от первого из 30;
- границы журнала при отказе: 60 в `T`, в `T + 59,999 с` — `429`, в `T + 60,000 с` — проходит;
- `429` из журнала при живом Redis в Redis не пишет: журнал `rate:{userId}` через `app.Redis`
  не изменился;
- снятие брони: через `app.Redis` в `rate:{userId}` положено 60 моментов (запросы других
  экземпляров), запрос — `429` с `Retry-After` от Redis; ключ удалён — 60 проходят подряд,
  61-й — `429`: брони от отказов не осталось;
- при отказе журналы разных пользователей не смешиваются;
- при отказе 70 одновременных запросов одного пользователя — ровно 60 не-`429`;
- unit на `LocalRateJournal` с фейковыми часами: обрезка, удаление пустых пользователей
  не чаще раза в окно, удаление не теряет одновременную бронь;
- после реализации — полный прогон: тесты 28.1 и `CardCacheRedisFailureTests` не правятся,
  упавший обсуждается.

## Найдено при реализации

- замок один на весь журнал, а не на пользователя: операции по микросекунде, а с замком
  на пользователя обход мог бы удалить список, в который соседний поток как раз добавляет бронь;
- лимит и окно вынесены из middleware в `RateLimitWindow`: их читают и скрипт, и журнал;
- тест снятия брони проходит и без журнала, поэтому проверен поломкой: без `Release`
  60-й запрос после удаления ключа получает `429`;
- запрос, оборванный клиентом во время вызова Redis, оставляет бронь в журнале до конца окна.
  Тестом не закрыто, поведение не менялось: сейчас это лишняя единица в счётчике, а не обход
  лимита;
- полный прогон: тесты 28.1 и `CardCacheRedisFailureTests` не правились.

## Найдено при реализации первой версии (bf995db)

- сделана в одном коммите с 28.1: без «стража» тесты 26.4 падали на `500`;
- тесты 26.4 (`CardCacheRedisFailureTests`) теперь ждут событие и метрику `rate-limit`
  перед событием кэша в каждом запросе при отказе — с согласия пользователя, проверки
  не ослаблены.
