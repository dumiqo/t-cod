# 26.2 Кэш и сброс

Статус: проработано

По решению задачи 25 (заметки, раздел «Кэш карточки») и проработке [задачи 26](26-card-cache.md).
Версия — из 26.1.

- первым тестом проверить, что `WithKeyPrefix` префиксует ключи `ScriptEvaluateAsync`, — иначе
  тесты разных `TestApp` делят ключи;
- `ICardCache` / `CardCache` над `IConnectionMultiplexer`, singleton: чтение поля `{id}` из
  `card:{userId}`, заполнение Lua-скриптом (версии нет или старше — замена hash `{v, id}`, равна —
  добавление поля, новее — ничего), надгробие после коммита (версии нет или старше — hash
  `{v: новая}`);
- снимок — JSON `EnrollmentCard` с настройками по умолчанию; тест: тело при попадании побайтно
  равно телу при промахе;
- надгробия пишет `EnrollmentService` после коммита, после событий, по одному вызову на
  пользователя: автору и каждому продвинутому, по версиям из результата 26.1;
- чужая карточка из кэша не отдаётся, вместо неё `404`; `404` не кэшируется — тест, что после
  продвижения карточка по id записи в очереди отдаёт бронь;
- каждая операция сбрасывает кэш так, что следующий запрос карточки видит её результат, в том
  числе в других карточках того же пользователя (остаток абонемента) и у продвинутого;
  в каждом тесте карточка сначала закэширована;
- `Cache:CardTtl`, по умолчанию 5 минут, проверка при старте 1 с ≤ x ≤ 1 ч; заполнение
  продлевает TTL, надгробие ставит его заново. Тесты: TTL ключа в Redis в пределах настройки
  после заполнения и после надгробия; значение вне границ (и на обеих границах) — старт падает
  или проходит;
- TTL в Redis идёт по реальному времени, фейковые часы его не двигают: если от TTL зависит
  поведение, тест на него — не переводом `app.Clock`;
- тест, что кэш используется: без него все тесты выше зелёные и без кэша. Изменить бронь в базе
  мимо API — карточка отдаёт прежнее значение (контракт это разрешает);
- новых событий и счётчиков нет;
- `ICacheService` для карточки не используется, поэтому промах `RedisCacheService.GetAsync`
  для значимых типов здесь не нужен.
