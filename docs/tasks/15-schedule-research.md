# 15. Исследование: расписание

Статус: проработано

- что хранить в токене продолжения и что делать с токеном от запроса с другими параметрами;
- принимать ли дату без времени в `from`/`to` — решено в задаче 7.3: принимать как полночь UTC.

Известно: в сидах 4 пары занятий с одинаковым временем начала, а задание сортирует только
по времени начала.

## Проработка

Согласованные решения; при выполнении задачи они записываются в заметки, раздел «Расписание».

Факты:

- в сидах 200 занятий через 432 минуты, у `i % 40 == 0` время начала копируется
  у предыдущего — 4 пары с одинаковым `startsAt` (39–40, 79–80, 119–120, 159–160), залы в паре
  разные. Отменены `i % 13 == 0` — 16 занятий, неотменённых 184. Занятие 39 отменено, поэтому
  в расписании видны 3 пары, а не 4: пары на границе страницы тест создаёт сам;
- Npgsql 9.0.3 (из `Npgsql.EntityFrameworkCore.PostgreSQL` 9.0.4) отбрасывает доли меньше
  микросекунды у параметра `DateTime`, не округляет. Проверено на временной таблице, строка
  `starts_at = 10:00:00`: параметр `10:00:00.0000001Z`, `.0000005Z` и `.0000009Z` сервер видит
  как `10:00:00` — `starts_at < @to` строку не даёт, `starts_at >= @from` даёт, хотя по контракту
  наоборот; `09:59:59.9999999Z` сервер видит как `09:59:59.999999`. Сырой Npgsql и LINQ
  через EF Core — одинаково.

Страницы:

- курсор по ключу, порядок `(starts_at, id)`: следующая страница — `(starts_at, id)` больше
  последнего отданного. `OFFSET` медленный на сотнях тысяч занятий и пропускает или повторяет
  занятия, если между страницами что-то отменили. `id` вторым ключом — пометка `// решение:`
  у `ThenBy`: порядок внутри одинакового `startsAt` контракт не задаёт;
- выборка `limit + 1` строк: лишняя строка есть — отдаём `limit` и токен, нет — `null`,
  в том числе страница ровно на `limit` занятий и пустой `items`;
- пустой `?continuationToken=` — то же, что отсутствующий, как `?roomId=` и `?limit=`
  по решению 7.3; значение из пробелов не разбирается — `400`;
- обход страниц — не снимок: следующие страницы показывают текущее состояние, отменённое
  занятие впереди не придёт, `freeSeats` и `mySeats` выданных страниц не пересчитываются.
  Курсор гарантирует, что неизменённое занятие придёт ровно один раз; время начала через API
  не меняется. Только строка в заметках.

Границы периода:

- `starts_at` выровнен по микросекунде, поэтому `starts_at >= from` равносильно
  `starts_at >= ceil(from)`, а `starts_at < to` — `starts_at < ceil(to)`. Обе границы перед
  запросом округляются вверх до микросекунды — `CeilingToMicroseconds` рядом
  с `TruncateToMicroseconds` в `WebApi/Time/TimeExtensions.cs`; пометка `// решение:` у вызова:
  Npgsql отбрасывает доли меньше микросекунды, вверх — чтобы граница осталась точной.
  Отказ на дробь длиннее 6 цифр расходится с 7.3 (до 7 цифр, формат `O`).

Токен:

- в токене — `from`, `to`, `roomId` запроса и курсор: `startsAt` и `id` последнего отданного
  занятия. `from`/`to`/`roomId` сверяются с query после разбора — UTC и округление вверх,
  поэтому `2026-01-01`, `2026-01-01T00:00Z` и `2026-01-01T03:00+03:00` — одни и те же
  параметры; несовпадение — `400`. `limit` не привязан: размер страницы между запросами менять
  можно. Пометка `// решение:` у сверки. Без привязки клиент, сменивший фильтр и не сбросивший
  токен, молча терял бы начало выдачи;
- без подписи и без привязки к пользователю: расписание видят все, `mySeats` считается по JWT,
  подделка лишь сдвигает начало выдачи. Подпись добавила бы ключ в конфигурацию и вопрос его
  смены;
- двоичный: байт версии `1`, `from` и `to` тиками, признак `roomId` (`0`/`1`) и `roomId`, если
  есть, `startsAt` курсора тиками, `id` курсора; base64url без `=` — токен идёт в query.
  Параметры хранятся значениями, не хешем: проще и нагляднее, лишние байты не важны;
- «не разбирается» — только форма: символы не из алфавита base64url (`+`, `/`, `=` тоже),
  длина после декодирования не та, что задаёт признак `roomId`, версия не `1`, признак не `0`/`1`,
  тики вне диапазона `DateTime`. Смысл не проверяется: курсор вне `[from, to)`, `id ≤ 0`,
  `from ≥ to` внутри токена безвредны — параметры всё равно совпадают с query, где `to > from`
  проверено; курсор до периода даёт выдачу с начала, после — пустую страницу;
- разбор — чистый класс (`Encode` / `TryDecode`) с юнит-тестами и тонкий model binder поверх,
  как в 7.3: ошибка в `ModelState` под ключом `continuationToken`, `400` отвечает
  `[ApiController]`. Сверку параметров binder не видит — она в действии:
  `ModelState.AddModelError("continuationToken", …)` и `ValidationProblem()`, вид тот же. Плохой
  токен вместе с другими неверными параметрами — все ошибки в одном `400`.

Тесты (в 16.1 и 16.3):

- граница: `startsAt = from − 1 тик` при `from` с тиком сверх микросекунды — не входит,
  `startsAt = to − 1 тик` — входит; юнит: `.0000001` → `.000001`, ровная микросекунда
  не меняется, `DateTime.MaxValue` не переполняется;
- пара с одинаковым `startsAt` ровно на границе страницы — на своих данных;
- обход засеянной базы за весь период сидов с `limit` 1, 2 и 7: последовательность `classId`
  совпадает с выборкой неотменённых занятий из свежего `DbContext` по `(starts_at, id)`;
- каждый признак «не разбирается» — юнит-тест разбора, плюс один интеграционный `400`;
  несовпадение `from`, `to`, `roomId` — `400`, смена `limit` — продолжение без ошибки.

Наблюдаемость: своих событий и счётчиков у расписания нет — `409` у него нет, `400` по задаче 6
не логируется и виден по `http.server.request.duration`; `operation = schedule` нужен только
для `429` (задача 28).
