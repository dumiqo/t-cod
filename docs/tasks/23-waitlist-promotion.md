# 23. Продвижение очереди

Статус: проработано

При отмене (§3) и уменьшении мест (§2). Проверка абонемента ожидающего — по итогам
задачи 21. Тесты на гонки и взаимоблокировку.

По решению задачи 4: под замком занятия прочитать очередь, затем свой абонемент и абонементы
всех ожидающих — одним запросом `ORDER BY id FOR UPDATE`. Блокировка двух абонементов
отдельными запросами крест-накрест дала взаимоблокировку, одним запросом по id — нет (проверено).
Пачками в порядке очереди блокировать нельзя: пачки ломают общий порядок по id (пример —
в заметках). Тест на встречные отмены: обе проходят, без `503`.

События (задача 6): продвижение каждого ожидающего — событие с `waitlistId`, `enrollmentId`
и местами, `club.waitlist.promoted` и списание его посещений; после коммита операции, которая
освободила места.

Разбита на подзадачи 23.1–23.4, каждая — свой коммит и своя строка статуса, порядок по номерам.
Правила продвижения — по решениям задач 21 и 22. Продвижение встраивается в код задач 12 и 14:
их тесты без очереди должны остаться зелёными без изменений.

## Проработка

Факты:

- `CancelAsync` и `ChangeSeatsAsync` сейчас: замок занятия, бронь, свой абонемент
  `LockByUserAsync` (отдельный запрос), затем `now`; `CheckAsync` проверяет `pass-expired`
  раньше `pass-exhausted`, срок — `ValidUntil < DateOnly.FromDateTime(now)`;
- абонемент есть у каждого засеянного пользователя, включая админов; отсутствие своего
  абонемента сейчас — `InvalidOperationException` (`500`);
- номера событий 3001 `WaitlistJoined` и 3002 `WaitlistLeft` заняты, 3003 и дальше свободны;
  счётчики очереди прибавляют места (`WaitlistJoined(seats)`);
- детерминированный порядок двух запросов на замке занятия уже применяется в 20.5:
  `WaitForBlockedCountAsync(1)`, затем второй запрос и `WaitForBlockedCountAsync(2)`.

Решения:

- **Замки и часы.** Часы читаются после последнего замка (задача 8), а набор абонементов
  нужно знать до `now`. Поэтому в §3 на неотменённом занятии и в §2 при уменьшении: замок
  занятия → бронь → очередь `waiting` этого занятия с отслеживанием по `id` → свой абонемент
  и абонементы всех ожидающих одним запросом `ORDER BY id FOR UPDATE` → `now` → проверки
  (`class-started` и т. д.). Если занятие уже началось — откат, лишние замки дёшевы.
  §3 на отменённом клубом занятии: очередь не читается, блокируется только свой абонемент.
  §2 при увеличении и при том же числе мест: очередь не читается, только свой абонемент — как
  сейчас; запрос с тем же числом мест ничего не освобождает и простаивающие места не раздаёт.
- **Ожидающий без абонемента** — `InvalidOperationException`, `500`, как у своего абонемента;
  молча не пропускается.
- **Порядок проверок у ожидающего:** своя запись (`own-release`) → места → `pass-expired` →
  `pass-exhausted`. Срок раньше остатка — как в шкале §1 (`CheckAsync`): при обеих бедах
  причина пропуска `pass-expired`.
- **Устройство кода.** Чистый план `WaitlistPromotion.Plan(freeSeats, entries, passesByUser,
  ownUserId, today)` — по каждой записи «продвинуть» или «пропустить с причиной», без базы;
  на него unit-тесты (порядок обхода, пропуски, граница `validUntil`, запись больше
  вместимости, `freeSeats ≤ 0`). Общий для §2 и §3 метод в `EnrollmentService` применяет план:
  брони с явным `Id`, записи → `promoted`, списание посещений. Свободные места —
  `capacity − SumActiveSeatsAsync` после `SaveChanges` своей операции. `CancelResult.Cancelled`
  и `ChangeSeatsResult.Changed` несут исходы продвижения для событий после коммита; ответы
  клиенту не меняются.
- **События и счётчики.** 3003 `WaitlistPromoted`: `waitlistId`, `enrollmentId` (одно число,
  оба поля), `classId`, `seats`, `userId`, `remainingVisits`. 3004 `WaitlistPromotionSkipped`:
  `waitlistId`, `classId`, `seats`, `userId`, `reason`. Оба Information. `club.waitlist.promoted`
  и `club.visits.charged` прибавляют места; `club.enrollments.created` не трогается — он про §1.
  Порядок после коммита: событие отмены или уменьшения, затем продвижения и пропуски в порядке
  очереди.
- **Общий запрос абонементов вводится в 23.1** — без него продвижение некорректно. Тест
  встречных отмен (23.3) поэтому сразу зелёный: красный прогон — временной поломкой (вернуть
  отдельный замок своего абонемента), вывод `503` — в отчёт, поломка откатывается.
