# 29.2 Сценарии на сидах

Статус: готово (c35ff6d)

Проверка на данных `DatabaseSeeder`, а не на созданных тестом: то, что увидит проверяющий
на чистой базе.

- сценарии из сидов:
  - занятия с 0, 1 и 2 свободными местами;
  - занятия, которые начнутся через 20–115 минут: фейковые часы стоят на моменте засева
    шаблона (решение задачи 5), поэтому это ровно 20–115 минут по часам теста;
  - занятия с одинаковым временем начала;
  - пользователь с двумя бронями по одному месту на одно занятие;
  - активные брони на отменённых занятиях;
  - абонементы с 0 и 1 посещением и просроченные;
- сиды остаются как есть: тест сначала находит нужное занятие или пользователя запросом
  к базе, а не по захардкоженному id — порядок засева может отличаться между прогонами;
- на каждый сценарий — запрос к своему эндпоинту с точным ответом и состоянием базы после
  (запись на последнее место, `capacity-exceeded` на полном, отмена ближе двух часов,
  карточка брони на отменённом занятии, `pass-exhausted` / `pass-expired`, расписание
  и загруженность с одинаковым временем начала);
- старт приложения на чистой базе (`docker compose down -v`, команды из `README`) —
  критерий готовности, проверяется вручную и записывается в отчёт.

## Что есть в сидах

Сверено по базе `club` при проработке. Сид детерминирован (`Random(20260101)`), от момента
засева зависят только времена; `i` — индекс занятия в сидере.

- `i = 100` начинается ровно в момент засева: по часам теста оно уже началось
  (граница «не раньше»);
- занятия через 20 / 50 / 80 / 100 / 115 минут: на первом броней нет, на остальных есть
  активные сидовые брони (1–2);
- по два занятия с 0, 1 и 2 свободными местами, все через 7 ч – 2 дня;
- пары с одинаковым началом в разных залах: `i = 39/40`, `79/80`, `119/120`, `159/160`;
  `i = 39` отменено (`i % 13 == 0`), у остальных пар оба активны, `119/120` и `159/160`
  в будущем;
- три пользователя с двумя бронями по одному месту на одно занятие, через 7–8 дней;
- 11 активных броней на отменённых занятиях: 4 в будущем, 7 в прошлом;
- абонементы: 0 посещений у каждого 20-го, 1 посещение у 10-го / 30-го / …, просрочены
  у каждого 17-го; `user034` и `user102` просрочены ровно на день, у `user170` абонемент
  просрочен и с одним посещением. Абонемента, действующего ровно по сегодня, в сиде нет —
  эту границу закрывают тесты задач.

## Как устроены тесты

- `WebApi.Tests/Seeds/SeedScenarioTests.cs`, один класс; поиск сидовых объектов —
  `Seeds/SeedQueries` (запросы через `app.CreateContext()`, всегда с порядком по `id`);
- каждый тест — свой `TestApp.StartAsync()` (свой клон, часы на моменте засева), вход
  найденным сидовым пользователем по email и `DatabaseSeeder.DefaultPassword`;
- нужного в сиде нет — `Assert.Fail` с описанием сценария («в сиде нет занятия с 1 свободным
  местом»). `Assert.Inconclusive` не берём: в прогоне он незаметен, сценарий тихо выпадет;
- ожидаемые значения (места, остаток, строки расписания и загруженности) считаются из базы
  до запроса; после запроса состояние читается через новый контекст; отказ проверяется
  «без следов» — места, остаток, ключ идемпотентности не изменились.

## Сценарии

### Места — §1, §7

- 1 свободное: `seats=1` → `201`, `freeSeats` 0, остаток −1; `seats=2` → `409
  capacity-exceeded` без следов;
- 2 свободных: `seats=2` → `201`, занято ровно до вместимости; `seats=3` →
  `capacity-exceeded`;
- 0 свободных: `seats=1` → `capacity-exceeded`; `POST /enrollments/waitlist` → `201`,
  `position: 1`;
- 2 свободных, очередь на 2 места → `seats-available`.

### Время — §1, §3

- запись на занятие через 20 минут (броней нет) → `201`;
- запись на занятие с `startsAt == now` → `class-started`;
- отмена сидовой брони на занятиях через 50 / 80 / 100 / 115 минут (`DataRow` по смещению,
  бронь ищется запросом) → `200`, `refundedVisits: 0`, места освобождены, остаток прежний;
- занятие через 115 минут, часы назад на 5 минут (до начала ровно 2 ч) → отмена с полным
  возвратом.

### Брони на отменённых занятиях — §2, §3, §4

Будущая и прошедшая бронь:

- карточка → `status: active`, `class.isCancelled: true`;
- `POST …/seats` → `class-cancelled`;
- отмена → `200`, полный возврат, остаток вырос на `seats`; у прошедшей — тоже,
  `class-started` не применяется.

### Две брони на одном занятии — §3, §4, §5

- расписание → `mySeats: 2`;
- отмена одной → `mySeats: 1`, вторая активна, её карточка не изменилась.

### Абонементы — §1

Пользователь ищется по остатку и `valid_until` относительно даты часов теста:

- 0 посещений → `pass-exhausted`;
- 1 посещение: `seats=1` → `201`, остаток 0; `seats=2` → `pass-exhausted`;
- просрочен на день → `pass-expired`;
- просрочен и с одним посещением, `seats=2` → `pass-expired` (приоритет причин, `NOTES.md`).

### Одинаковое время начала — §5, §6

- расписание за окно с будущей парой → оба занятия, порядок по `id`; при `limit=1` —
  по одному на страницу, без пропусков и повторов;
- пара с отменённым → в расписании только неотменённое;
- загруженность за день пары → по строке на каждый зал, отменённое не входит ни
  в `classesCount`, ни в `totalCapacity`.

## Старт на чистой базе

Вручную при реализации, перед `docker compose down -v` — подтверждение пользователя (том
с dev-базой удаляется). Затем команды из `README`; в «Результат» — вывод `/health/ready`,
логина `user001` и `GET /schedule`.

## Красная фаза

Одна временная поломка на группу, не коммитится:

| группа | поломка |
|---|---|
| места | `>=` вместо `>` в проверке вместимости |
| время | `>` вместо `>=` в «занятие началось» |
| два часа | не обнулять возврат |
| отменённое занятие | убрать исключение из `class-started` |
| `mySeats` | брать места одной брони |
| приоритет абонемента | поменять местами `pass-expired` и `pass-exhausted` |
| расписание | убрать фильтр отменённых |

Красная фаза — все семь поломок из таблицы выше дали красное в своей группе (места — 2,
время — 1, два часа — 4, отменённое занятие — 1, `mySeats` — 1, приоритет абонемента — 1,
расписание — 1 упавший тест).

Нюансы:

- запись в очередь занимает ключ идемпотентности (решение задачи 20.4), поэтому снимок «без
  изменений» у `JoinWaitlist_FullSeededClass` ждёт `keys=1`;
- «часы назад на 5 минут» — `FakeTimeProvider.AdjustTime` (`SetUtcNow` назад не умеет), вход —
  уже после перевода часов;
- `Enrollment.Class` под глобальным фильтром: брони на отменённых занятиях ищутся только с
  `IgnoreQueryFilters()`;
- у карточки второй брони после отмены первой меняется только `pass.remainingVisits` (+1),
  остальное сравнивается целиком.
